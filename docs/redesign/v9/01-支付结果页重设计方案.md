> 范围：`newuniapp/src/packages/pkg-order/pages/payment-result/payment-result.vue`（09 屏「支付结果」）。
> 预览：`docs/redesign/v9/02-支付结果页UI预览.html`（390px 手机画框，5 态实时切换：定金+问卷 / 全款 / 确认中 / 待确认 / 档期锁失败补偿）。

## 0. 一句话结论

旧版成功态是「一个印章 + 三张白卡」，确认中/待确认则整块交给 `result-page`（`min-height: 100vh`）——三态像三个产品，且成功页没有订单号、支付时间、流水号与款项进度。

v9 把三态收束为同一套高定语言：

**深墨黑金仪式头（眉标 + 压印金印 + 结论 + 档期铭牌）→ 撕口 → 暖白收据（实付 + 款项进度 + 真实凭证细目）→ 异常补偿提示 → 接下来时间轴 → 双按钮吸底**

确认中 / 待确认不再使用 `result-page`，改为同源暖白仪式卡（信息蓝双环状态印 + 轮询进度 / 流水号与安心指引），首屏不再被 100vh 撑破。

## 1. 现状问题审查

重设计前逐行比对旧版 `payment-result.vue`（667 行）与 `result-page.vue`、`order.vue`、后端 `OrderPayLogic::getPayStatus()`，确认 7 个结构性问题：

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **正文字号低于可读下限** | `.kv__k/.kv__v` 均为 `--fs-22`（11px），备注/时间戳大量 `--fs-18/20`（9–10px） | 金额与时间等关键凭证在真机上难读，违反 tokens「正文 ≥ 24rpx」 |
| 2 | **三态视觉割裂** | 成功态自绘印章 + 白卡；pending/unconfirmed 走 `result-page`：`min-height: 100vh`、`success-circle-fill` / `clock-fill` 大图标、另一套按钮排布 | 同一个支付结果页，三态看起来像三个产品 |
| 3 | **`result-page` 高度溢出** | `result-page.vue:94` `min-height: 100vh` + `padding: 120rpx ... + safe-bottom`，外层 `page-shell` 又为吸底栏预留 `--bottom-bar-h` | 小屏首屏被撑出滚动条，操作按钮被推到第二屏 |
| 4 | **凭证信息缺失** | 成功页只有「服务档期 / 主持人 / 举办场地」三行；无订单号、无支付时间、无支付流水号、无实付渠道 | 用户要联系客服时无法快速定位；「这是一张收据」的信任感不足 |
| 5 | **款项进度缺失** | 只有一个大金额，没有「已付 / 待付尾款 / 总额」 | 定金用户无法确认自己还差多少 |
| 6 | **异常补偿完全静默** | 后端 `getPayStatus` 已返回 `payment_exception` / `payment_exception_desc` / `refund_id`，旧页只读 `pay_status` | 档期锁失败自动退款时，用户仍看到「支付成功」，会重复下单或投诉 |
| 7 | **「接下来」不可操作、无状态** | 数字序号列表，问卷节点不可点；无「已完成」锚点；不足 2 项才隐藏 | 支付完成后的第一动作（填问卷）埋在一个不可点的行里 |

同时保留旧版全部业务铁律（见 §2），只改表现层与字段采集。

## 2. 业务与状态铁律（100% 保留）

1. **支付结果唯一可信来源仍是 `/pay/payStatus` 轮询**：`POLL_INTERVALS = [1, 2, 3, 5, 8, 13]`，不凭路由参数直接判成功。
2. **订单摘要来自 `getOrderDetailV2(orderId)`**：失败只降级摘要区块并给「重新加载」，不影响已确认的支付结果。
3. **`unconfirmed` ≠ 失败**：不出现红叉、`--c-danger`、「失败」字样或「重新支付」；只给「刷新结果」幂等回查（`queryPayState()`，不发起 prepay）。
4. **`pending` 不抢主操作**：底部只给 ghost「查看订单」，配文字入口「返回首页」（O2 + O14）。
5. **缺订单号**：保持 `<base-empty status="error" :error-kind="'business'" ... />`（动态绑定，过 R1 门禁）。
6. 关闭语义走 `#nav-left` 的 `pnav-close`，不把支付页压回返回栈。

## 3. 设计方向：黑金定档礼笺

### 3.1 视觉母题

支付成功不是「系统提示」，而是一张**可以留存的定档礼笺**：

- **上半区深墨**：承接 `detail.vue` 的 `ohero` 与 `v7/activity.vue` 的置顶票根，用 `--c-dark-1/2/3` 三段墨色渐变建立仪式感；香槟金只出现在眉标、印章与档期铭牌上。
- **撕口分隔**：左右半圆缺口 + 1rpx 虚线，和 v7 电子票根一脉相承；缺口露出 `--c-bg`，让礼笺「浮」在暖象牙底上。
- **下半区暖白**：真正的收据区，所有可核对的钱与凭证都在这里，全部左对齐、tabular-nums、无装饰色。
- **压印金印**：全站唯一允许的金色渐变（`--c-brand-soft → --c-brand → --c-brand-text`），`seal-in` 220ms 只播一次。

### 3.2 三态统一

| 态 | 容器 | 主视觉 | 主操作 | 次操作 |
|---|---|---|---|---|
| `success` | 黑金礼笺 + 暖白收据 | 压印金印 | `ink` 查看订单 / 填写问卷 | `ghost` 返回首页 / 查看订单 |
| `pending` | 同源暖白仪式卡 | 信息蓝双环印 + 呼吸描边 | 无 `ink`（O2） | `ghost` 查看订单（通栏）+ 文字「返回首页」 |
| `unconfirmed` | 同源暖白仪式卡 | 信息蓝双环印（静态） | `ink` 查看订单 | `ghost` 刷新结果 + 文字「返回首页」 |

确认中与待确认共用 `.state-card`（`--c-surface` + `--c-line-strong` + `--r-lg`），只是徽章动效、轮询胶囊、指引区不同；不再引入 `result-page` 的第二套排版。

## 4. 信息架构与字段真实来源

### 4.1 成功态信息层级

```
01 深墨仪式头
   ├─ PAYMENT CONFIRMED（英文眉标，serif）
   ├─ 压印金印（112rpx，双环）
   ├─ 支付成功（fs-2xl）
   ├─ 安心副标题（异常时改为自动退款说明）
   └─ 已锁档 · YYYY.MM.DD 周X（仅真实 service_date 且非异常）
02 撕口
03 暖白收据
   ├─ 本次实付 + 已入账/退款处理中（status-tag）
   ├─ ¥ 金额（price xl，18:1 对比）
   ├─ 定金 · 微信支付
   ├─ 款项进度三栏（仅定金模式且 total>0、need_pay>0）
   └─ 订单凭证
       ├─ 订单编号 + 复制
       ├─ 服务档期
       ├─ 服务团队
       ├─ 举办场地
       └─ 支付时间
04 异常补偿（仅 payment_exception=1）
05 接下来（≥2 个真实节点才渲染）
06 吸底双按钮
```

### 4.2 字段真实来源表

| 展示字段 | 优先来源（`/pay/payStatus`） | 回退（`getOrderDetailV2`） | 再回退 | 说明 |
|---|---|---|---|---|
| 支付状态 | `res.pay_status` / `res.payment.pay_status` | — | — | `1` 才进入成功；轮询超时只转待确认 |
| 本次实付 | `res.payment.pay_amount` | `order.paid_amount` → `pay.paid_amount` → `pay.pay_amount` | 路由 `amount` | 先认本次流水金额，避免累计已付混淆 |
| 款项阶段 | `res.payment.pay_type_desc`（定金/尾款/全款） | `pay.current_pay_stage` + `deposit_paid` / `balance_paid` 推导 | — | 「未知」不作为阶段文案 |
| 支付时间 | `res.payment.pay_time` | `res.order.pay_time` → `order.pay_time` | — | 统一格式化 `YYYY.MM.DD HH:mm` |
| 支付流水号 | `res.payment.payment_sn` | — | 路由 `payment_sn` | 待确认态可复制，便于客服定位 |
| 订单编号 | `res.order.order_sn` | `order.order_sn` | — | 带「复制」轻按钮 |
| 异常补偿 | `res.payment_exception`(0/1) | `res.order.payment_exception` | — | 为真时隐藏档期铭牌、切换副标题与金额状态 |
| 异常说明 | `res.payment_exception_desc` | — | 固定兜底文案 | 后端原话优先 |
| 退款单号 | `res.refund_id` | — | — | `>0` 时在异常卡内展示 |
| 服务档期 | — | `order.service_date` | — | `YYYY.MM.DD 周X`；无真实值不显示 |
| 服务团队 | — | `items[].staff.name` + `items[].package.name` | — | 过滤 `item_status === 3`（已取消），多项追加「等 N 项」 |
| 举办场地 | — | `order.address` | — | 无值不显示 |
| 款项进度 | — | `pay.deposit_amount` / `order.paid_amount` / `pay.need_pay_amount` / `order.total_amount` | — | 仅定金模式展示 |
| 待填问卷 | — | `pending_questionnaire` | — | 决定时间轴节点与底部主按钮 |
| 尾款节点 | — | `pay.need_pay_amount` + `pay.current_pay_stage` | — | `>0 && stage !== 'paid'` 才出现 |

**原则**：任何字段取不到都不编造。能降级的区块降级（摘要 / 时间轴），不能降级的关键结论（是否支付成功）只由轮询决定。

## 6. 交互与异常策略

1. **轮询节奏不变**，第 n 次轮询后 `fbPollText(n, 6)` 更新；6 格圆点逐格点亮，第 3 次仍会通过 `aria-live` 播报标题。
2. **成功动作**：
   - 有待填问卷：左「查看订单」+ 右「填写新人问卷」（`ink`）。
   - 无待填问卷：左「返回首页」+ 右「查看订单」（`ink`）。
   - 时间轴问卷节点整行可点，右侧「去填写 ›」胶囊。
3. **待确认动作**：底部「刷新结果」（ghost，`:loading="rechecking"`）+「查看订单」（ink）；回查成功直接切成功态并补拉摘要，回查未知提示 `FB.PAY_RECHECK_UNKNOWN`。
4. **异常补偿**：`payment_exception=1` 时
   - 副标题改为固定说明「款项已收到，档期锁定异常，系统已自动发起原路退款」；
   - 金额标签变 warning「退款处理中」；
   - 隐藏档期铭牌与「完成支付并锁定档期」时间轴节点；
   - 展示后端异常说明与退款单号（有值时）。
5. **摘要失败**：只把「订单凭证」换成「订单摘要没取到 + 重新加载」，礼笺头部、金额、时间轴不受影响。
