# 订单确认页（08 屏）重设计方案

> 范围：`newuniapp/src/packages/pkg-catalog/pages/booking/booking.vue` 的第 08 步「订单确认」，含页面结构、交互流程、异常状态、视觉与组件规范、机型适配。
> 预览：`docs/redesign/v6/02-订单确认页UI预览.html`（390 首屏 / 390 下半屏 / 地址弹层 / 320 窄屏 / 异常态）。
> 依据：现有 3171 行 `booking.vue`、`shared/contracts/dto.ts` 的 `QuoteSummary` / `BookingPreviewResponse`、`src/styles/tokens.css`、`pm 组件库现状（page-shell / bottom-bar / price / agreement-check / base-empty / status-tag）`。
> 目标：把「一张大订单卡」改成「一份能逐项核对的确认单」，让用户在支付前 10 秒内回答三个问题：**这单是什么、钱怎么算、什么时候付多少**。

---

## 0. 一句话结论

现在是一张卡里塞完套餐、人员、附加项、联系人、地址，再跟一张「支付安排 + 金额」卡；重设计后拆成：

**墨色服务摘要（3 秒确认）→ 01 套餐与服务 → 02 附加项 → 03 联系人 → 04 服务地址 → 05 价格明细 → 06 支付安排 → 备注 → 协议 → 吸底单一 CTA**

每个区块独立成卡、独立可改；报价失败只坏「05/06」两块，不再整页替换；主按钮在报价未就绪时变成「重新获取报价」而不是灰着。

## 1. 现状盘点

### 1.1 页面在流程里的位置

```
人员详情（05）
  → 选日期 + 地区（弹层，决定算价）
  → booking?staff_id&package_id&date&region
      step 1  选套餐        （bhero 860rpx 大图 + 套餐横滑卡）
      step 2  附加项        （bhero + 附加项横滑卡）
      step 3  管家（可选）   （后台 booking_butler_enabled 开启才有）
      step 4  督导（可选）
      step N  订单确认      ← 本文范围
  → createOrder → prepay → wx.requestPayment
  → 09 payment-result（轮询 /pay/payStatus）
```

确认页不是独立路由，而是 `booking.vue` 里 `isConfirm = step === confirmStep` 的一个分支（`confirmStep = 2 + 可选角色数 + 1`）。**这个结构不改**：确认页复用已选状态、报价上下文和锁档生命周期，拆成独立页会带来三份重复状态。

### 1.2 现有结构（模板 324–560 行）

| 区块 | 现在展示什么 | 结构问题 |
|---|---|---|
| 订单卡 `.ord` | 日期（MM.DD / 年份周几）、`城市 · 地址`、`套餐名 · 14:00`、状态角标「已锁档 / 锁定中 / 待支付 / 待确认」、锁档倒计时 | 六类信息挤在一张卡；`14:00` 是**硬编码**（`booking.vue:352`），后端没有服务时间字段 |
| 同一张卡继续 | 服务人员头像 + 姓名 + 套餐名；管家/督导行 | 「人员」和「套餐」没有层级，扫读时找不到边界 |
| 同一张卡继续 | 附加项 N 项、逐行价格、加购推荐 | 附加项是第二重要的钱，却排在人员之后、用虚线分隔 |
| 同一张卡继续 | 联系人 + 服务地址，各带一个「更换」 | 两个「更换」打开**同一个弹层**（姓名/手机/地址/备注混在一起），改地址要跨过联系人字段 |
| 支付卡 `.card2` | 定金/尾款两节点 + 金额四行（套餐/附加项/管家督导/合计） | 「什么时候付」和「钱花在哪」混在一张卡；定金/尾款与合计之间没有等式关系 |
| 提示块 `.block` | 金额不一致、支付失败、服务端校验，全是同一种琥珀色 warning 块 | 阻断性错误和非阻断提示同色同形，用户不知道哪个必须处理 |
| 协议 | 默认未勾，未勾时按钮不置灰、点按出红字 | ✅ 这是全站正面范式，保留 |
| 吸底栏 | 左「应付定金 + 金额」，右「上一步 + 微信支付」 | 「上一步」与导航返回重复；按钮在报价未就绪时 `:disabled`，只能看到「金额待确认」的灰按钮 |

### 1.3 七个需要修的结构性问题

1. **没有「服务摘要」，只有「订单卡」**
   确认页丢掉前三步的 860rpx 大图后，直接进入白卡，视觉上像换了一个产品。用户第一眼看不到「哪一天、跟谁、在哪」这三件事的完整组合。

2. **关键信息失真**
   `{{ heroTitle }} · 14:00` 写死下午两点。后端 `PackageVO` 只有 `duration_desc`，没有 `service_time`。**设计上必须删除这个时间**，而不是继续显示一个可能错误的时间。

3. **改一条信息要退好几步**
   套餐、附加项、联系人、地址都没有就地入口，只能底栏「上一步」逐级退。确认页恰恰是用户最常发现「套餐选错了」的地方。

4. **价格与支付割裂**
   定金/尾款在「支付安排」，套餐/附加项/合计在下面；用户要自己在两处拼出「今天付 1280，尾款 2000，总共 4680」。

5. **异常状态没有优先级**
   `amountMismatch`（必须阻断）、`payError`（可重试）、`validations`（服务端校验）共用 `.block` 样式（`booking.vue:490–520`），视觉权重完全一样。

6. **报价失败整页替换**
   `quoteState === 'failed'` 时整个确认面板换成 `base-empty`（`booking.vue:327–342`）。用户刚核对完的套餐、人员、地址全部消失，只剩一个「重新获取报价」。

7. **信息字号低于可读下限**
   附加项行、联系人行、地址行、锁档提示大量使用 `--fs-18/20/21`（9–10.5px）。`tokens.css` 明确「最小 24rpx=12px，正文 28rpx=14px」，确认页是**法律与金额相关**的页面，不应靠小字塞信息。

### 1.4 必须保留的业务铁律

以下来自现有代码注释与后端时序，重设计只改表现层，不动这些：

- 金额只消费服务端 `quote` 字段；支付前断言 `定金 + 尾款 === 总额`，不等即阻断。
- 报价失败不沿用旧价；`quote_hash` 为空即视为未就绪。
- 下单顺序固定：校验 → `createOrder`（幂等）→ 读 `need_pay / current_pay_stage` → `prepay` → `requestPayment`。
- 不做「下单成功就支付」；后端待确认订单不能 `prepay`。
- 锁档 TTL 900s；锁档失败（别人先锁）必须拦，锁档接口异常放行。
- 协议默认未勾；未勾时按钮不置灰，点按出红字。
- 支付结果只认 09 页轮询，不认 `requestPayment` 的 success。

## 2. 设计目标与原则

| 原则 | 具体做法 | 反例（现在） |
|---|---|---|
| **一页核对** | 摘要卡 + 6 个带序号的清单块，每块只回答一个问题 | 一张卡混装六类信息 |
| **可改可回** | 每个块右上角「修改」，直接回到对应步骤或弹层 | 只有「上一步」 |
| **金额单一事实源** | 05 只做「钱花在哪」，06 只做「什么时候付多少」；两处金额都直接读 `quote` | 定金在 06、合计在 06 底部，中间夹着明细 |
| **错误就近** | 报价错误留在 05/06；支付错误贴在协议上方；校验错误按级别分色 | 全部堆在页面底部 |
| **不假装知道** | 没有服务时间就不显示；没有优惠就不显示优惠行；尾款没开放日就写「婚礼前 7 天开放」 | 硬编码 14:00 |
| **一个主 CTA** | 吸底只有 1 个 ink 按钮；次要动作全部进各块「修改」 | 「上一步 + 微信支付」并排 |

### 2.1 信息优先级（用户阅读顺序）

```
3 秒    ┌ 哪一天 · 什么套餐 · 跟谁 · 在哪 ──────── 摘要卡
5 秒    ├ 套餐/人员对不对 ────────────────────── 01
        ├ 附加项买了什么 ────────────────────── 02
10 秒   ├ 联系人/地址对不对 ──────────────────── 03 / 04
        ├ 钱怎么算 ──────────────────────────── 05
        └ 今天付多少、尾款什么时候付 ──────────── 06
决策    └ 协议 → 去支付 ─────────────────── 吸底
```

### 3.2 区块规格总表

| # | 区块 | 回答的问题 | 是否必填 | 数据来源 | 缺失兜底 |
|---|---|---|---|---|---|

| 01 | 套餐与服务 | 买的什么、谁来服务 | 是 | `currentPackage`、`packageRules`、`duration_desc`、`staffName/Avatar`、`quoteRoleRows` | 套餐名回落「服务套餐」；无时长不显示该行 |
| 02 | 附加项 | 加购了什么、多少钱 | 否 | `selectedAddonList`、`addonPrice`、`upsellAddon` | 空态「未加购附加项，可直接提交」 |

| 05 | 价格明细 | 钱花在哪 | 是 | `quote.service_amount / addon_amount / deposit_amount / balance_amount / total_amount`、`quoteItems`（角色行） | 报价失败 → 块内错误 + 重试 |

### 3.3 逐块规格

#### 00 服务摘要（墨色卡）

- **形态**：`linear-gradient(135deg, #211d19 0%, #14110f 100%)`，圆角 `--r-lg`（40rpx），内边距 30rpx。它是确认页唯一的深色面，用来承接前三步的沉浸感，但不占 860rpx。
- **内容顺序**：
  1. eyebrow：`ORDER REVIEW`（serif 20rpx，`--c-brand-soft`，字距 2rpx）——装饰性英文小标，允许低于正文字号。
  2. 状态胶囊：右上角，`status-tag` 的语义色（浅底），文案见 §5.2。
  3. 日期：`MM.DD`（64rpx serif，白）+ `2027 · 周四`（24rpx，`--c-on-dark-2`）。
  4. 套餐名：32rpx / 600 / 白，最多 2 行。
  5. 人员 · 地区：24rpx，`--c-on-dark-2`，单行省略。
  6. 锁档行：`clock` 图标 + 说明（24rpx）+「改期」文字按钮（24rpx 下划线）。底部 1rpx `rgba(255,255,255,.12)` 分隔。
- **交互**：
  - 点「改期」→ 打开现有「服务日期与地区」弹层；确认后走 `confirmPicker` 的既有链路：`invalidateQuote` → 清角色候选 → 静默重载 → `runPreview` + `doLock`。
  - 摘要卡整体不可点（避免误触改期）；只有「改期」是热区（88rpx 高）。
- **不显示金额**：金额在 05 和吸底出现两次已经足够；摘要是「事实」，不是「报价」。

#### 01 套餐与服务

- **头**：序号 `01`（24rpx serif，`--c-brand-text`）+ 标题「套餐与服务」（28rpx / 600）+ 右侧「修改 ›」（24rpx，`--c-ink-3`）。
- **行**：
  - `套餐` / 套餐名 + 单价（右，serif 28rpx）。单价取 `pkgPrice(currentPackage)`，与 05 的 `service_amount` 可能因地区不同，**以 05 为准**，这里只做识别。
  - `服务时长` / `duration_desc`（如「8 小时现场服务」）。无值整行不渲染。
  - 分隔线（1rpx `--c-line`）。
  - 服务人员：56rpx 头像（圆角 `--r-sm`）+ 姓名（28rpx / 600）+ 角色说明（24rpx `--c-ink-3`：「主持人 · 4.9 分 · 128 单」，有则拼）。
  - 可选角色行：`管家` / `督导` + 人员名 + 价格。无则整段不渲染。
  - 套餐规则 `packageRules`：24rpx `--c-ink-3`，最多 2 行，作为块尾注释。
- **修改**：回 step 1。若当前已锁档，回退不释放锁（用户可能只是看看）；重新进入确认页时 `invalidateQuote` 已让旧报价失效，会自动重算。
- **空/异常**：套餐被下架时 `load({silent:true})` 已过滤不可售项，这里只做名称兜底，不额外报错。

#### 02 附加项

- **头**：`02` + 「附加项 · N 项」；N=0 时标题只写「附加项」。
- **行**：名称（28rpx，单行省略）+ `+¥300`（serif 28rpx，右对齐，不换行）。
- **小计**：≥2 项时出现 `小计 +¥600`；1 项时不重复。
- **空态**：一行 24rpx `--c-ink-3`「未加购附加项，可直接提交」+ 右侧「去挑选」文字按钮（→ step 2）。
- **加购推荐**：保留现有 `upsellAddon`，但降级为块底一条建议条（`--c-surface-2` 底、24rpx），右侧「+¥200 加上」pill。**不出现百分比**（后端没有该数据）。
- **修改**：回 step 2。

#### 03 联系人

- **头**：`03` + 「联系人」+「修改」。
- **内容**：`林小满 · 138****8888`（28rpx / 500）；下一行 24rpx `--c-ink-3`「用于档期确认与到场联系」。
- **缺失**：`未填写联系人`（28rpx，`--c-danger`）+「去填写」。
- **修改**：打开**联系人弹层**，只含「姓名」「手机号」两个字段。地址拆到 04，避免改电话要跨过地址。
- **校验**：姓名 ≥2 字；手机 `/^1\d{10}$/`；错误贴字段下方（`base-input` 现有能力）。

#### 04 服务地址

- **头**：`04` + 「服务地址」+「修改」。
- **第一行**：`浙江省 · 杭州市 · 西湖区` + `定价地区` 小标签（`tone-primary`，24rpx）。这一行回答「按哪算价」。
- **第二行**：详细地址（28rpx，最多 2 行）。
- **注释**：24rpx「地区决定套餐价格；详细地址用于服务人员到场」。
- **修改**：打开**地址弹层**：
  - 顶部只读行「服务地区：浙江省 · 杭州市 · 西湖区」，右侧「修改地区 ›」→ 关闭弹层、打开日期+地区弹层（**地区与日期必须一起改**，因为两者共同决定报价与档期）。
  - 「详细地址」输入框（必填）。
  - 保存只校验地址，不触发报价。
- **为什么地区不在地址弹层里直接改**：改地区 = 改价 + 改可约人员 + 改锁档，必须走统一的日期/地区弹层，否则会出现「地址改了、价格没变」的假状态。

#### 05 价格明细

- **头**：`05` + 「价格明细」，无「修改」（价格不可直接编辑）。
- **行**：`套餐金额` / `附加项（N 项）` / `管家 / 督导`（仅 >0）/ `优惠`（后端未提供，不渲染）。
- **合计**：分隔线后 `合计` + `¥4,680`（40rpx serif / 600）。
- **脚注**：24rpx「价格由系统按服务日期与地区计算，以提交时为准」。
- **报价中**：三行 32rpx 高骨架 + 合计骨架；脚注换「正在核价…」。**不显示旧金额**。
- **报价失败**：块内替换为错误卡（红/琥珀），文案「报价没有算出来」+「价格必须以服务端报价为准」+「重新获取报价」按钮。**其他区块保持可见**。
- **金额不一致**：合计下方红条「定金 + 尾款 ≠ 总额，已阻断支付」+「重新获取报价」。这是阻断态，主按钮点击也会被 `handleSubmit` 拦下。
- **数据口径**：`addon_amount` 含关联角色金额，页面用 `addon_amount - rolePriceSum` 拆出纯附加项；`total_amount` 直接展示，不在前端相加。

#### 06 支付安排

- **形态**：纵向时间轴，两节点或单节点。
  - 两段（`deposit > 0 && balance > 0`）：
    ```
    ● 今天 · 支付定金            ¥1,280
    │ 微信支付，支付后档期锁定
    ○ 尾款                      ¥3,400
      婚礼前 7 天开放支付
    ```
  - 一段（`balance <= 0` 或缺失）：`● 今天 · 支付全款 ¥4,680` +「微信支付」。
- **文案来源**：
  - 定金时机：`quote.payment_mode_desc`，兜底「今天支付」。
  - 尾款时机：`quote.balance_pay_desc` / `balance_desc`，兜底「婚礼前 7 天开放支付」。
  - **不编具体日期**：后端没有 `balance_open_date`，写「婚礼前 7 天」而不是「05.13 开放」。
- **支付方式**：只写「微信支付」，不做选择器（小程序内只有这一种可用，做选择器是假选择）。
- **说明**：节点副文案已经承担「支付后锁档 / 服务号提醒」，**块尾不再重复整段说明**（重复会把 06 撑高，也会削弱节点本身的权重）。
- **与 05 的边界**：06 不重复「套餐/附加项/合计」，只出现「定金/尾款/全款」三个语义。

#### 07 备注

- **形态**：折叠行，`备注` + 右侧「填写」/「修改」；已填时显示一行摘要（28rpx，省略）。
- **编辑**：弹层内原生 `textarea`（200 字，`maxlength`，显示计数）。保存只写 `form.remark`，**不触发报价**。
- **为什么放在 06 之后**：备注不影响金额；放在价格之前会打断「核对 → 付钱」的节奏。

#### 08 协议

- 保留 `agreement-check`：默认未勾、未勾不置灰、点按出红字。
- 文案保留现有「我已阅读并同意《预约服务协议》与《售后服务规则》，定金支付后档期即锁定。」
- 位置固定在吸底栏上方，与 CTA 同屏可见。

#### 09 吸底栏

```
┌──────────────────────────────────────┐
│ 应付定金                    [去支付] │
│ ¥1,280 · 合计 ¥4,680                  │
└──────────────────────────────────────┘
```

- 左：两行。第一行 label（24rpx `--c-ink-3`「应付定金」）；第二行 `price size="lg"` + 同行小字「合计 ¥4,680」（24rpx `--c-ink-3`，基线对齐）。
- 右：`base-button variant="ink" size="md"`，宽度自适应，最小 240rpx。
- 高度沿用 `--bottom-bar-h`（128rpx）。**不写第三行**：`--bottom-bar-h` 只够 108rpx 内容行，再加一行会在小屏挤压安全区；尾款信息已经在 06 块里说清楚。
- 320px 下允许隐藏「合计 ¥…」小字（金额本身仍是主信息），按钮文案不缩写。
- **去掉「上一步」**：导航返回键已绑定 `onBack → prevStep`，底栏再放一个是重复；省下的宽度给主 CTA。

## 4. 主流程

### 4.1 进入确认页

```
用户点「下一步 · 确认订单」
  ├─ ensureDateTime()：缺日期/地区 → 开弹层，不放行
  ├─ 角色步骤校验：需要但没选人 → toast，不放行
  ├─ step = confirmStep
  ├─ resetScrollAfterStepChange()
  ├─ quoteState !== 'ready' → runPreview()
  │     ├─ v2 /v2/bookingPreview → 成功：quote + items + validations + quote_hash
  │     └─ 失败 → v1 /order/preview 兜底
  │            └─ 都失败：quoteState='failed'（只坏 05/06）
  └─ doLock()：lockSchedule(900s)
        ├─ 成功 → lockState='locked'，本地倒计时 15:00
        ├─ 业务失败（已被锁/不可约）→ lockState='failed'，提示改期
        └─ 接口异常 → lockState='error'，放行，文案说真话
```

页面同时把 `contact_default` 的姓名/手机填入空字段（不覆盖用户已输入）。

### 4.2 提交与支付

```
点「去支付」
  ├─ ① 协议未勾 → agreeError + 滚动到协议（不置灰按钮）
  ├─ ② validate() 失败 → 打开联系人弹层（聚焦第一个错误字段）
  ├─ ③ lockState === 'failed' → 阻断，提示改期
  ├─ ④ quoteState !== 'ready' / quote_hash 空 → runPreview + toast，本次不提交
  ├─ ⑤ amountMismatch → 阻断，提示重新报价
  ├─ ⑥ barAmount === null → 阻断，提示金额缺失
  ├─ ⑦ submitting = true（防连点）
  ├─ ⑧ checkAvailable()：is_available === false → 阻断；接口异常 → 放行
  ├─ ⑨ createOrder(params + quote_hash)（后端幂等）
  │     ├─ 无 order_id → 报错
  │     └─ 有 order_id → 记 orderId
  ├─ ⑩ 读 need_pay / current_pay_stage
  │     ├─ 不可支付 → toast「订单已提交，待确认后可支付」→ redirect 订单详情
  │     └─ 可支付 → payOrder(id)
  ├─ ⑪ prepay({from:'order', order_id, pay_way:2})
  │     └─ 无 config → 报错
  ├─ ⑫ requestPayment(config)
  │     ├─ cancel / fail → payError 内联，留在本页可重试
  │     └─ success → redirect 09 payment-result（结果以轮询为准）
  └─ finally submitting=false
```

### 4.3 能不能支付：判定表

| 条件 | 结果 | 页面表现 |
|---|---|---|
| 协议未勾 | 不提交 | 协议红字 |
| 联系人/地址缺失 | 不提交 | 开联系人弹层 + toast |
| `lockState = failed` | 不提交 | 红色警示条 +「换日期」 |
| `lockState = expired` | 先重锁 | 警示条 +「重新锁档」；点击后 `doLock()` |
| `quoteState != ready` | 先重报价 | 主按钮文案「重新获取报价」，点击即重取 |
| `quote_hash` 空 | 先重报价 | 同上 |
| `amountMismatch` | 不提交 | 合计下红条 |
| `barAmount = null` | 不提交 | 主按钮「金额待确认」，点击重报价 |
| 以上全通过 | 提交 | 按钮「去支付」 |

> 关键：**没有任何一种情况把按钮做成无解释的灰**。不可提交时按钮文案本身说明下一步动作（重报价 / 重新锁档），点击可执行。

### 4.4 支付后的分流

| 服务端返回 | 跳转 | 说明 |
|---|---|---|
| `need_pay = none` / `current_pay_stage` 不在 deposit/full/balance | 订单详情 | 待确认订单不能 prepay |
| 可支付且 `requestPayment` 成功 | 09 支付结果 | 带 `order_id / payment_sn / amount`，由 09 轮询 |
| `requestPayment` 取消/失败 | 留在本页 | 内联错误 +「重新支付」/「查看订单」 |

### 5.1 状态矩阵

| # | 触发 | 表现位置 | 表现 | 主操作 | 阻断 |
|---|---|---|---|---|---|
| 1 | 缺 `staff_id` | 整页 | `base-empty business`「预约信息不完整」 | 返回重选 | 是 |
| 2 | 配置加载失败 | 整页 | `base-empty error` + 重试 | 重试 | 是 |
| 3 | 报价计算中 | 05/06 | 骨架 + 「正在核价…」；底栏按钮「核价中…」 | 等待 | 是 |
| 4 | 报价失败 | 05/06 | 块内错误卡 +「重新获取报价」 | 重试 | 是 |
| 5 | 金额不一致 | 05 合计下 | 红条「定金 + 尾款 ≠ 总额」 | 重新报价 | 是 |
| 6 | 锁档中 | 摘要卡 | 胶囊「锁档中」 | 无 | 否 |
| 7 | 锁档成功 | 摘要卡 | 胶囊「档期已保留」+ 倒计时 | 改期 | 否 |

| 10 | 锁档超时 | 摘要卡 + 协议上方 | 胶囊「档期已释放」；条「保留已超时，请重新锁档」 | 重新锁档 | 是 |
| 11 | 服务端校验 error | 协议上方 | 红色校验列表（档期/不可约/资质） | 按 code：换日期 / 联系客服 | 是 |
| 12 | 服务端校验 warn | 协议上方 | 琥珀条 | 继续 | 否 |
| 13 | 提交失败 | 协议上方 | 错误卡 +「重新提交」 | 重试 | 是 |
| 14 | 支付取消/失败 | 协议上方 | 错误卡「支付未完成」+「重新支付」「查看订单」 | 重试/查看 | 是 |
| 15 | 支付结果未知 | 09 页 | 轮询中 / 超时兜底 | 查看订单 | — |
| 16 | 401 未登录 | 登录页 | 登录返回后自动补报价 + 锁档 | 登录 | — |
| 17 | 地区变更 | 摘要卡 | 旧锁释放 → 重报价 → 重锁 | 等待 | 是（临时） |

### 5.2 锁档五态（摘要卡胶囊）

| `lockState` | 胶囊文案 | Tone | 小字 | 主按钮 |
|---|---|---|---|---|
| `idle` | 待支付 | warning | 支付成功前档期不为你预留 | 去支付 |
| `locking` | 锁档中 | neutral | 正在为你锁定档期… | 核价/锁档中… |
| `locked` | 档期已保留 | success | 保留 14:32，超时重选 | 去支付 |
| `failed` | 档期被占用 | danger | 该档期刚被订走，请换一个日期 | 换日期 |
| `expired` | 档期已释放 | warning | 保留时间已到，请重新锁档 | 重新锁档 |

> 现状把「超时」也塞进 `failed`，导致倒计时归零后仍提示「该档期刚被锁定」——文案是错的。重设计拆出 `expired`，因为两者的下一步动作不同：被抢必须改期，超时可以原地重锁。

### 5.3 报价四态

| `quoteState` | 05 表现 | 06 表现 | 吸底 |
|---|---|---|---|
| `idle` | 空行骨架 | 不渲染 | 「核价中…」 |
| `loading` | 骨架 +「正在核价…」 | 骨架 | 「核价中…」 |
| `ready` | 四行 + 合计 | 时间轴 | 「去支付」 |
| `failed` | 错误卡 + 重试 | 不渲染 | 「重新获取报价」（可点） |

### 5.4 错误分级与视觉

| 级别 | 用途 | 底色 / 描边 / 文字 | 位置 |
|---|---|---|---|
| `danger`（阻断） | 金额不一致、档期被占、校验 error、提交失败 | `--c-danger-bg` / `--c-danger-border` / `--c-danger` | 05 合计下、协议上方 |
| `warning`（需注意） | 锁档异常、校验 warn、支付未完成 | `--c-warning-bg` / `--c-warning-border` / `--c-warning` | 协议上方 |
| `info`（说明） | 支付前不预留、地区影响价格 | `--c-surface-2` / `--c-line` / `--c-ink-3` | 块内注释 |
| `success` | 档期已保留 | `--c-success-bg` / `--c-success-border` / `--c-success` | 摘要卡胶囊 / 锁档行 |

同一屏**最多 1 条 danger + 1 条 warning**；多条校验合并进同一张卡的列表，不叠 3 张卡。

### 5.5 文案口径

- 不承诺没发生的事：锁档异常时不说「已保留」，说「支付成功前不为你预留」。
- 不吓唬：支付失败不说「未扣款」（可能已扣），说「支付未完成，可重新支付或查看订单」。
- 不甩锅给网络：业务不可用不说「网络开小差」，用 `resolveErrorView` 的 `business` 态。
- 金额错误必须给动作：所有涉及金额的阻断都配「重新获取报价」，不只说「请重试」。

## 7. 组件规范

### 7.1 `confirm-section`（新增）

确认页 6 个块的统一外壳，避免每块手写一遍标题与「修改」。

```vue
<confirm-section index="01" title="套餐与服务" action="修改" @action="editStep(1)">
  ...
</confirm-section>
```

| Prop | 类型 | 默认 | 说明 |
|---|---|---|---|
| `index` | `string` | `''` | 两位序号，空则不渲染 |
| `title` | `string` | 必填 | 区块标题 |
| `action` | `string` | `''` | 右侧动作文案，空则整块无动作 |
| `actionAria` | `string` | `action` | 读屏文案 |

| Event | 说明 |
|---|---|
| `action` | 点右侧动作 |

- 根节点：`view.confirm-section`，卡片样式内置。
- 结构：`head`（序号 + 标题 + 动作）+ `body`（默认插槽）。
- 动作热区高度 88rpx，视觉字号 24rpx；右侧 chevron 24rpx。
- 不在组件内做权限/禁用判断；由页面决定是否传 `action`。

### 7.2 摘要卡

页面私有（`.cf-sum`），不抽组件：它绑定了 6 个页面状态（日期、套餐、人员、地区、锁档、改期），抽象出去会变成一堆 props。

### 7.3 信息行

统一两类，页面私有 class：

- `.cf-row`：`label（26rpx ink-3） + value（28rpx ink，右对齐/可换行）`。
- `.cf-row--stack`：label 在上、value 在下（地址、套餐规则用）。

### 7.4 支付时间轴

`.cf-pay`：左侧 1rpx 竖线 + 节点圆点（18rpx），节点间距 24rpx；当前节点实心 ink，未来节点空心 `--c-line-strong`。金额在节点右上角，serif 32rpx。

### 7.5 内联提示

`.cf-alert` 三变体：`--danger` / `--warning` / `--info`。结构固定为 `icon + 文案（flex 1）+ 动作（可选）`；文案可多行，动作不换行。

### 7.6 吸底栏

复用 `bottom-bar`，不改组件契约。左侧 `.cf-bar`，右侧 `base-button`。`has-note` 不启用（协议在内容流末尾，不在吸底）。

## 8. 机型适配

### 8.1 基准与断点

设计基准 750rpx（= 390px 设计稿 × 1.923）。rpx 随屏宽线性缩放，需要专门处理的只有三处：**字号下限、吸底栏宽度、长文本换行**。

| 机型 | 逻辑宽 | 1rpx | 页面边距 | 摘要日期 64rpx | 吸底金额 48rpx | 结论 |
|---|---|---|---|---|---|---|
| iPhone SE 1 / 老安卓 | 320 | 0.427px | 17.9px | 27.3px | 20.5px | 基准下限，需窄屏规则 |
| iPhone SE 2/3、8 | 375 | 0.5px | 21px | 32px | 24px | 标准 |
| iPhone 12–15 | 390 | 0.52px | 21.8px | 33.3px | 25px | 设计基准 |
| Android 主流 | 360 | 0.48px | 20.2px | 30.7px | 23px | 与 375 同构 |
| iPhone 15 Pro Max | 430 | 0.573px | 24.1px | 36.7px | 27.5px | 上限，字号不再放大 |

### 8.2 窄屏（≤ 340px）规则

1. 摘要日期 64rpx → 56rpx；套餐名 32rpx → 30rpx。
2. 吸底主按钮最小宽度 240rpx → 220rpx，文案「去支付」不缩写（6 字在 220rpx 内可容纳 24rpx 字号）。
3. 吸底摘要「合计 ¥4,680 · 尾款 ¥3,400」在 320px 下可能换行——允许换成两行，底栏高度自适应（不写死高度，用 `min-height`）。
4. 价格行 label 最长「管家 / 督导」6 字，320px 下仍可与金额同行；更长的 label 必须 `ellipsis`。
5. 弹层宽度 100%，内边距 30rpx；联系人两字段在 320px 下仍竖排（`layout="row"` 的标签宽 128rpx，输入区剩余 ≈ 200px，可用）。

### 8.3 大字号与字体缩放

- 微信「字体大小」调到最大时，`rpx` 不缩放，但系统字体会放大。所有容器**不写死高度**（除头像、圆点），用 `min-height` + `padding`。
- 价格行使用 `flex-wrap: wrap`：金额不换行，label 可换行。
- 摘要卡日期与套餐名之间用 margin，不用绝对定位，避免字体放大后重叠。

### 8.4 安全区与键盘

- 吸底：`padding-bottom: calc(var(--sp-2) + var(--safe-bottom))`，由 `bottom-bar` 负责；`page-shell` 的 `bottomBar` 负责内容留白。
- 键盘：确认页正文无输入框，备注/联系人/地址都在弹层；弹层内 `cursor-spacing="120"`，避免输入框贴键盘。
- 弹层最大高度 80vh，内容可滚；底部按钮固定在弹层底部，不随内容滚走。

### 8.5 长文本

| 字段 | 规则 |
|---|---|
| 套餐名 | 摘要卡 2 行截断；01 行内 1 行截断 |
| 人员名 | 1 行截断，最大 160rpx |
| 附加项名 | 1 行截断，价格不换行 |
| 地址 | 2 行截断（`ellipsis-2`） |
| 套餐规则 | 2 行截断 |
| 备注摘要 | 1 行截断 |
