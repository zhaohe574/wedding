# 预约支付与档期状态流转规则（v6 增补）

> 范围：确认页提交校验、`去支付 → 待确认` 分流、订单详情状态表达、人员详情档期/地区切换。
> 关联：`01-订单确认页重设计方案.md`、`02-订单确认页UI预览.html`。
> 日期：2026-11-10。本文既是产品规则，也是本轮代码改动的验收依据。

---

## 0. 一句话结论

四个问题其实是一条链上的四个断点：

```
选日期/地区（人员详情）
   → 核对并提交（确认页）
   → 订单创建后能不能付（待确认 / 待支付）
   → 付不了时看什么、点什么（订单详情）
```

本轮把每个断点都改成「**状态可见 + 下一步可执行 + 失败不丢上下文**」：

| 需求 | 结论 |
|---|---|
| 必填项未填 | 不弹窗、不整页报错；滚动到首个出错块 + 闪烁 3 次 + 块内红字，提交被拦 |
| 去支付但付不了 | 订单创建后进入「待确认」，确认页只读并给「查看订单」；订单详情解释原因与等待时间 |
| 订单详情 | 状态 → 下一步 → 服务信息 → 待办 → 金额 → 动作，一屏最多两个按钮 |
| 人员详情 | 直接进入默认第二天；档期与地区都可换；不可约时「去候补」与「换档期」并列 |

## 1. 需求 1：提交时的必填校验

### 1.1 校验顺序与规则

点「去支付」后按固定顺序校验，**命中第一个错误就停**，不把所有错误一次性倒给用户。

| 顺序 | 字段 | 规则 | 错误文案 | 归属块 |
|---|---|---|---|---|
| 1 | 协议勾选 | 必须勾选 | 请先勾选《预约服务协议》再支付 | 协议行 |
| 2 | 联系人姓名 | 非空、≥2 字 | 请输入联系人姓名 / 姓名至少 2 个字 | 03 联系人 |
| 3 | 联系人手机 | `/^1\d{10}$/` | 请输入手机号 / 手机号格式不正确 | 03 联系人 |
| 4 | 服务地址 | 非空 | 请输入服务地址 | 04 服务地址 |
| 5 | 锁档 | 未被抢、未超时 | 该档期刚被订走，请换一个日期 / 请重新锁档 | 摘要卡上方 |
| 6 | 报价 | `quoteState=ready` 且有 `quote_hash` | 正在重新获取报价，请稍候 | 05 价格明细 |
| 7 | 金额 | 定金 + 尾款 = 总额、应付金额非空 | 报价金额不一致，已阻断支付 | 05 价格明细 |

> 协议校验保持现状：未勾选时按钮不置灰，点按后在协议行下出红字（合规 D4）。必填字段则走「定位 + 闪烁」。

### 1.2 为什么是「定位到块」而不是「定位到输入框」

03/04 的字段在底部弹层里，页面上没有常驻输入框。如果点提交后直接弹层，用户看不到「到底哪一块缺了」，闪烁也失去意义。因此：

```
点「去支付」
  → validate() 失败
  → 标记 formErrorVisible
  → 计算首个出错块（联系人优先于地址）
  → 滚动到 #cf-contact / #cf-address（导航高 + 120px 呼吸位）
  → 该块描边/底色闪 3 次（1.4s）
  → 块内出现红字：「请填写联系人姓名、手机号」
  → 不自动开弹层；用户点该块右上角「修改」就地编辑
```

**不自动开弹层的理由**：弹层会立刻盖住刚滚到的位置，用户看不到「哪一块错了」；而「修改」入口就在块头，点一下即可，代价很小。

### 1.3 页面反馈状态

| 状态 | 触发 | 页面表现 | 退出条件 |
|---|---|---|---|
| `idle` | 进入确认页 | 无红字、无闪烁 | 点「去支付」 |
| `error-shown` | 校验失败 | 首个出错块闪烁 + 红字；页面滚到该块 | 字段被修正 |
| `editing` | 点「修改」 | 弹层打开，字段错误贴在输入框下 | 保存且校验通过 |
| `cleared` | 所有字段通过 | 红字消失；再点「去支付」进入提交 | — |

实现要点：

- 闪烁只作用于块容器（`confirm-section` 的 `flash` prop），不做位移，避免整块跳动。
- 滚动用 `createSelectorQuery` 取块位置，`pageScrollTo` 280ms；偏移 120px 防止块顶被导航压住。
- 红字是块级文案，但**精确到字段**：「请填写联系人姓名、手机号」而不是「请完善信息」。

## 2. 需求 2：`去支付` 与「待确认」

### 2.1 关键事实

后端时序（`OrderPayLogic::getPayableOrder`）：

```
createOrder → order_status = 0（待确认）
   → 商家确认，或 1 小时自动确认
   → order_status = 1（待支付）
   → 才允许 prepay
```

所以「去支付」**不保证当场能付**。这不是前端能绕过的，页面必须把「创建成功但暂不可付」当成正常分支，而不是异常。

### 2.2 提交状态机

```
                 ┌──────────── 校验失败（滚动+闪烁）────────────┐
                 ▼                                             │
IDLE ──点去支付──> VALIDATING ──通过──> SUBMITTING ──createOrder──> CREATED
                                                          │
                          ┌───────────────────────────────┼────────────────────────────┐
                          ▼                               ▼                            ▼
                   CREATE_FAILED                    NOT_PAYABLE                   PAYABLE
                   （内联错误，可重试）          （order_status=0 待确认）      （deposit/full/balance）
                          │                               │                            │
                          └── 留在本页重试                 │                     PREPAYING → PAYING
                                                          │                            │
                                              ┌───────────┴──────────┐        ┌────────┴────────┐
                                              ▼                      ▼        ▼                 ▼
                                       弹窗说明 + 查看订单      留在本页    取消/失败          成功
                                       （确认页转只读）        「查看订单」  （订单已存在）    → 09 结果页
```

### 2.3 判定「现在能不能付」

只读服务端字段，不在前端按状态猜：

```ts
const stage = String(res?.current_pay_stage || '')
const needPay = String(res?.need_pay || '')
const payable = stage ? ['deposit', 'full', 'balance'].includes(stage) : needPay !== 'none'
```

| 服务端返回 | 含义 | 前端动作 |
|---|---|---|
| `current_pay_stage = deposit/full/balance` | 可付 | `prepay` → `requestPayment` |
| `need_pay = none` | 不可付 | 进入待确认分支 |
| 两个字段都缺 | 保守处理 | 视为不可付，进入待确认分支 |

### 2.4 确认页的界面反馈

**按钮文案（按状态覆盖，不是固定一个）**

| 状态 | 文案 | 点击行为 |
|---|---|---|
| 正常可提交 | 去支付 | 校验 → 创建订单 |
| 报价失败 | 重新获取报价 | 重新报价 |
| 锁档被抢 | 重新选择日期 | 打开日期/地区弹层 |
| 锁档超时 | 重新锁档 | 原地重锁 |
| 提交中 / 支付中 | 提交中… / 支付中… | 无（loading） |
| 订单待确认 | 查看订单 | 跳订单详情 |
| 订单已建、支付失败 | 重新支付 | 直接重试 prepay，不重复下单 |

> 「去支付」是主路径文案；一旦已知不可执行，按钮必须换成能执行的动作。**不存在点了没反应的灰按钮**。

**不可支付时的弹窗**

```
标题：订单已提交
正文：当前无法支付，订单状态已变为「待确认」。
      商家确认后即可继续支付，通常 1 小时内完成。
按钮：查看订单（唯一）
```

点确认后 `redirectTo` 订单详情；页面不留在确认页让用户反复点「去支付」。

**订单创建后的确认页**

- 订单一旦创建（无论待确认还是支付失败），所有「修改 / 改期 / 加购」入口立即隐藏，页面进入只读态。
- 理由：订单已经落库，再改套餐/地址不会影响已创建的订单，只会让用户误以为改了。
- 吸底：label 变「待确认」，金额隐藏（显示 `—`），按钮「查看订单」。
- 页面顶部出现琥珀条：「订单已提交，等待商家确认」+「查看订单」。

### 2.5 订单状态流转（全链路）

| 状态 | 值 | 触发者 | 用户可见 | 允许的用户动作 |
|---|---|---|---|---|
| 待确认 | 0 | 用户创建订单 | 「待确认」+「商家确认后开放支付」 | 取消订单、联系顾问、查看详情 |
| 待支付 | 1 | 商家确认 / 1 小时自动确认 | 「待支付」+ 支付倒计时 | 支付定金/尾款、取消、改期（按 actions） |
| 待服务 | 2 | 支付成功 | 「待服务」+ 服务日期 | 填问卷、改期、暂停、联系顾问 |
| 服务中 | 3 | 到达服务日 | 「服务中」 | 联系顾问 |
| 已完成 | 6 | 服务完成 | 「已完成」 | 评价、售后 |
| 已取消 | 8 | 用户/商家取消 | 「已取消」 | 重新预约 |
| 已退款 | 9 | 退款完成 | 「已退款」 | 重新预约 |
| 退款中 | 10 | 发起退款 | 「退款中」 | 查看进度 |

> 页面动作只认 `actions` / `action_reasons`，不用 `order_status` 自行推导「能不能付、能不能取消」。

## 3. 需求 3：订单详情的信息层级与操作

### 3.1 信息层级（从上到下）

```
① 状态     深色 hero：状态 chip → 一句状态解释 → 婚礼倒计时/日期 → 已付/待付/总额
② 下一步   待确认说明条（仅 status=0）；里程碑（有数据才显示）
③ 服务     人员、档期、场地、附加项、联系人
④ 待办     问卷 / 尾款 / 评价（只有真实待办才出现）
⑤ 金额     订单金额、已支付、可退、待支付
⑥ 动作     底栏：一个主按钮 + 至多一个次按钮；取消订单退到页尾文字链
```

### 3.2 状态展示规则

| 状态 | Chip | 状态解释（hero 下方） | 说明条 | 底栏 label | 主按钮 |
|---|---|---|---|---|---|
| 待确认 0 | 待确认 | 等待商家确认后开放支付 | 「通常 1 小时内完成；确认前请勿重复下单」+ 联系顾问 | 待商家确认 | 联系顾问 / 填问卷 |
| 待支付 1 | 待支付（+ 定金已付） | 请在倒计时结束前完成支付 | — | 待支付 | 支付定金/尾款/全款 |
| 待服务 2 | 待服务 | 服务已确认，请按约定时间到场 | — | 已付清 | 填写问卷（如有） |
| 服务中 3 | 服务中 | 服务进行中 | — | 已付清 | 联系顾问 |
| 已完成 6 | 已完成 | 服务已完成，可发表评价 | — | 已付清 | 评价 |
| 已取消 8 | 已取消 | 订单已取消 | — | — | 重新预约 |
| 已退款 9 | 已退款 | 退款已完成，到账时间以支付渠道为准 | — | — | — |
| 退款中 10 | 退款中 | 退款处理中，到账时间以支付渠道为准 | — | — | — |

规则：

- **状态名不重复解释**：chip 已经写「待确认」，下面不再写「订单待确认」，只写「为什么 + 多久 + 下一步」。
- **倒计时只在待支付出现**；其他状态用一句解释占位，避免 hero 高度忽高忽低。
- **待确认不显示「待支付」金额语义**：金额仍可展示为订单总额/已付，但底栏 label 必须是「待商家确认」。

### 3.3 操作按钮规则

| 规则 | 说明 |
|---|---|
| 一屏最多 2 个底栏按钮 | 主按钮 1 个 ink；次按钮至多 1 个 ghost |
| 主按钮只做「现在最该做的一件事」 | 按 `actions.pay` → 问卷 → 联系顾问 的顺序取第一个可用 |
| 不出现重复入口 | 主按钮已经是「联系顾问」时，次按钮不再放「联系顾问」 |
| 破坏性动作降级 | 「取消订单」从底栏移到页尾文字链，避免与支付/咨询抢位 |
| 售后优先于咨询 | `can_user_refund` 为真时，次按钮是「订单售后」，否则才是「联系顾问」 |
| 不可用动作不渲染 | 没有 `actions.pay` 就不出现支付按钮，不用灰按钮占位 |

### 3.4 「待确认」的专项处理

这是本轮最容易误解的状态：

- 订单已创建、**钱还没付**、**档期是否锁定取决于后端**，用户不能做任何支付动作。
- 页面必须明确三件事：为什么不能付（等商家确认）、要等多久（通常 1 小时内）、现在能做什么（联系顾问 / 取消 / 查看）。
- 不允许出现「支付定金」按钮或「待支付 ¥X」底栏，否则用户会反复点。

## 4. 需求 4：人员详情的档期与地区

### 4.1 默认值规则

| 场景 | 日期 | 地区 |
|---|---|---|
| 入口带 `date` | 用入口日期 | 入口 > 缓存 > 空 |
| 直接进入（搜索/扫码/分享，无 date） | **第二天** | 缓存 > 空 |
| 从列表/查档期进入 | 入口日期 | 入口地区 |

- 直接进入默认第二天，是为了让用户一进来就看到「明天能不能约」，而不是空白档期。
- **地区不默认到「第一个开通区县」**：那会让用户在不知情的情况下按一个没选过的城市算价。没有地区就显示「选择地区」，点 CTA 先补地区。
- 默认日期若早于排期规则的最早可约日，按规则夹紧到最早可约日。

### 4.2 切换入口

身份卡的可约行从「只读文本」变成可点行：

```
● 5月21日 周四 · 杭州 · 可约        更换 ›
```

点击打开「档期与地区」弹层：

- 上半：自绘月历（与预约页同一口径，6 行固定高度、切月不跳、超出规则范围禁用）。
- 下半：省/市/区三栏（`region-columns`）。
- 底部：未选完时按钮文案直接说明缺什么（请选择日期 / 请选择地区），选完变「查看该档期」。
- 确认后：写回 `date + region` → 存 `booking_context` → 重新加载详情（价格、可约状态、套餐）。

### 4.3 可约状态与 CTA 矩阵

| 日期状态 | 地区 | 主按钮 | 次按钮 | 点击主按钮的反馈 |
|---|---|---|---|---|
| 可约 | 已选到区县 | 预约档期 | 先咨询 | 带 date + region 进预约页 |
| 可约 | 未选 | 预约档期 | 先咨询 | 打开档期/地区弹层 + toast「请选择服务地区后继续」 |
| 已满/不可约 | 已选 | 去候补 | 换档期 | 带 date + region 进候补申请 |
| 已满/不可约 | 未选 | 去候补 | 换档期 | 打开弹层补地区，再进候补 |
| 选人模式（管家/督导） | 固定 | 选择 TA | — | 回预约页写入角色人员，不改档期 |

> 关键变化：不可约时不再只有「去候补」一个出口，旁边永远有「换档期」；身份卡行也随时可点。

### 4.4 状态流转

```
进入详情
  ├─ 有 date → 按该日期加载
  └─ 无 date → 明天（按规则夹紧）
        ↓
   getStaffDetail(date, region)
        ├─ schedule_available = true  → CTA「预约档期」
        └─ schedule_available = false → CTA「去候补」+ 次按钮「换档期」
                                          ↓
                                    打开「档期与地区」
                                          ↓
                                    选日期 + 省市区 → 确认
                                          ↓
                                    saveBookingContext → 重新加载
                                          ↓
                              可约 → 「预约档期」；仍不可约 → 「去候补」
```

### 4.5 异常与边界

| 场景 | 表现 | 处理 |
|---|---|---|
| 排期规则接口失败 | 日历按「今天起」兜底 | 不阻断；不显示不存在的最大日期 |
| 详情加载失败 | 整页 `base-empty error` + 重试 | 保留已选日期/地区，重试沿用 |
| 地区三栏加载失败 | 弹层内显示空态 | 保留日期，允许重试；不静默用全国价 |
| 默认第二天早于最早可约日 | 自动夹紧到最早可约日 | 用户不会一进页就选中禁用日期 |
| 选中的日期在规则外 | 日历禁用该日，不能确认 | 按钮文案「请选择日期」 |
| 未选地区点预约 | 打开弹层 + toast | 不带着空地区跳转 |
| 选人模式 | 隐藏「更换」，禁止开弹层 | 角色人员必须与预约上下文一致 |

## 5. 跨页一致性

| 数据 | 写入 | 读取 | 约束 |
|---|---|---|---|
| `date + region` | 人员详情切换、预约页弹层 | 详情/预约/候补/报价 | 统一走 `booking-context`，不各页各存 |
| `quote_hash` | 确认页报价成功 | `createOrder` | 套餐/附加项/人员/日期/地区任一变更即失效 |
| 锁档 | 确认页进入 | 提交前二次 `checkAvailable` | 900s TTL；离开页面释放 |
| `order_id` | `createOrder` 成功 | 支付、查看订单 | 有订单后不再 `createOrder`，只重试 `prepay` |
| 订单状态 | 服务端 | 确认页/订单详情 | 前端不推导，只读 `actions` / `order_status` |

### 5.1 登录中断

- 确认页 401 → 登录页 → 返回后补一次报价 + 锁档；**不自动重放 `createOrder`**。
- 人员详情 401 → 登录返回后沿用原 date/region 重新加载。

### 5.2 网络与重复点击

- 提交按钮 `submitting/paying` 双锁；`createOrder` 带幂等键。
- 支付取消/失败：订单已存在，按钮变「重新支付」，只重试 `prepay`。
- 报价过期：提交前发现 `quote_hash` 为空 → 重新报价 + toast，本次不提交。

## 6. 文案口径

| 场景 | 文案 | 禁止 |
|---|---|---|
| 确认页主按钮 | 去支付 | 「提交并支付」（与实际可支付性不符） |

| 校验失败 | 请填写联系人姓名、手机号 / 请填写详细地址 | 「请完善信息」 |
| 锁档被抢 | 该档期刚被订走，请改期 | 「系统繁忙」 |
| 锁档超时 | 保留时间已到，可重新锁档 | 「该档期刚被锁定」（超时≠被抢） |
| 不可约 CTA | 去候补 / 换档期 | 只给「去候补」 |
| 默认日期 | 明天（可换） | 空白日期 |

- [ ] 待确认状态 chip/解释/说明条/底栏四处口径一致。
