### 2.2 缺口（这些是本次 24 屏会撞到的，需主理人裁决是否改 `src/request`）

| 缺口 | 具体表现 | 影响 | 建议 |
|---|---|---|---|
| **无 token 刷新** | 全仓库没有 refresh 接口，`mnpLogin` 每次生成新 token | 401 后只能重新 `wx.login`；多端会互踢 | 不新增，保持「单 token + 401 重登」。**页面不要缓存用户态做权限判断** |
| **Idempotency-Key 每次重试都换新** | key 在 `doRequest` 内生成（`:163`），每次重试都是新 key → 后端无法识别为重放 | 一旦给写接口配 `retry>0`，重复建单风险回来了 | 建议把 key 上提到 `request()` 生成并在重试间复用。**属 `src/request` 改动，需裁决** |
| **无请求取消** | 未保留 `requestTask`，无 abort | 快速切页后在飞请求仍会 toast / setState | 页面用「页面级 `isActive` 守卫」缓解，不必改请求层 |
| **无分级超时** | 全局 60s，`payStatus` 轮询也用 60s | 弱网下支付结果页会白等 | 轮询调用显式传 `timeout: 8000` |
| **v2 熔断粒度太粗** | 一个 404 关掉全部 v2（C-02 会触发） | 一个路径写错，四屏聚合全废 | 短期靠修路径规避；中期建议按 path 记录 |
| **无缓存 / SWR** | `utils/cache.ts` 只存 token | 分类/地区每次进页面都请求 | 分类树、地区树用 `utils/cache` 加 10 分钟 TTL |
| **无运行时校验** | 契约字段全靠 TS 静态 | 后端加字段无感，改语义会静默错 | 见 §7.3，写 `assertShape` 开发环境校验，不引第三方依赖 |

### 6.3 缺口字段的「编译期提醒」技巧

缺口字段全部 optional，编译器不会报错——所以要在**运行时**提醒：

```ts
// src/utils/assertShape.ts（建议新增，纯手写，不引依赖）
export function assertShape<T>(value: unknown, required: Array<keyof T & string>, tag: string) {
    if (import.meta.env.PROD) return           // 生产不校验，零开销
    if (!value || typeof value !== 'object') {
        console.warn(`[contract] ${tag} 返回非对象`, value)
        return
    }
    const missing = required.filter((k) => (value as any)[k] === undefined)
    if (missing.length) console.warn(`[contract] ${tag} 缺字段：${missing.join(', ')}`)
}
```

页面用法：`assertShape<StaffCardVO>(item, ['id', 'name'], 'staff/lists')`

### 7.1 新增 `src/composables/usePagedList.ts`（列表页统一，禁止各页各写）

```ts
import { computed, ref, type Ref } from 'vue'
import { normalizePage } from '@/request'
import type { ApiPaged, LoadPhase } from '@/api/types'

export interface UsePagedListOptions<T, Q extends Record<string, any>> {
    /** 取一页；必须自己 catch 后 rethrow，交给 composable 统一处理 */
    fetcher: (query: Q & { page: number; page_size: number }) => Promise<unknown>
    /** 变更条件时置空，用于「条件变化 → 回顶重拉」 */
    query: Ref<Q>
    pageSize?: number
    /** 首屏是否立即拉取 */
    immediate?: boolean
}

export interface UsePagedListReturn<T> {
    list: Ref<T[]>
    total: Ref<number>
    phase: Ref<LoadPhase>
    refreshing: Ref<boolean>
    loadMoreStatus: Ref<'idle' | 'loading' | 'nomore' | 'error'>
    /** 首屏/条件变化：清空 + 回第一页 */
    reload: () => Promise<void>
    /** 触底：追加下一页（重复调用安全） */
    loadMore: () => Promise<void>
    /** 下拉刷新 */
    refresh: () => Promise<void>
}

export function usePagedList<T, Q extends Record<string, any>>(
    options: UsePagedListOptions<T, Q>
): UsePagedListReturn<T>
```

要点（这些都是现网 5 个列表页各写一遍、各有 bug 的地方）：
- `phase` 只用 `LoadPhase` 五态，空态由 `list.length === 0 && total === 0` 判定
- `loadMore` 必须防重入（`if (loadingMore) return`），否则触底会连发 3 次
- 条件变化必须 `list=[]` + `uni.pageScrollTo({scrollTop:0})`，否则旧数据混入新条件
- 失败时 `loadMoreStatus='error'` 让用户点重试，**不要静默吞掉**

| ~~Idempotency-Key 上提到 `request()` 并在重试间复用~~ | `request/index.ts:278` | ❌ **原描述「现在每次重试换新 key，幂等形同虚设」已过期**。源码 `:278` 是 `const idempotencyKey = config.idempotent ? … : ''`，在**重试循环之前**定一次，`:284` 每次重试都传同一个；`doRequest`（`:170`/`:194`）只负责塞 header，不生成 | 🚫 **不需要改**。本轮未动代码，只在 `index.ts:188-194` 补了一条**不变式注释**，防的是「未来有人把生成挪回 doRequest」，而不是描述一个不存在的现状 |

**裁决附注：为什么否决「按 `errorCode` 建白名单判断可重试」**
1. **治不了主因**：500 走信封路径时 `payload.error_code` 多数不存在 → 500 的 `errorCode` 是 `undefined` → 会被判不可重试，**把该重试的干掉**；
2. **`errorCode` 是业务语义，`statusCode` 是传输语义**。用业务码做传输判断，每新增一个 errorCode 都要重新判断"这个要不要重试"，而 `statusCode >= 500` 永远不会因为业务加码而漂。

> ⚠️ **本节自己也踩过一次坑**：本表第一版写「Idempotency-Key 现在每次重试换新」，据此下了改动指令，开发核源码后驳回——代码早已修好，是**文档过期**。教训：文档描述现状时也会过期，**判定"缺陷是否成立"必须以源码为准，文档只能用来定位范围**。

### 8.2 支付状态机（09 / 10 / 22 共用，**不允许改**）

```
createOrder → order_status=0 待确认
        ↓ 商家确认 or 1 小时自动确认（后端 OrderPayLogic）
order_status=1 待支付 ──prepay──► payment_sn 待支付流水
        ↓ wx.requestPayment
    ┌── cancel ──► 回订单详情，可再次 prepay（复用同一流水）
    ├── fail   ──► 提示重试，30s 内不许重发
    └── success ─► 只是「用户完成动作」，不是支付成功
                        ↓
              poll getPayStatus（1/2/3/5/8/13 秒）
                        ↓
        pay_status=1 ─► success（可显示成功页）
        pay_status=0 且用完间隔 ─► unconfirmed（禁止显示失败、禁止重付）
        再次 prepay 前必须 queryPayState：paid→成功 / unknown→禁止重付
```

**新 UI 的红线**：
1. 09 屏必须在 `poll` 拿到 `pay_status=1` 之后才能渲染「支付成功」印章。**不允许**用 `requestPayment` 的 `success` 直接跳成功页。
2. 09 屏「刷新结果」= 回查，不发 `prepay`。
3. 10 / 22 屏的「去支付」必须在 `actions.pay === true` 时才可点，读 `action_reasons.pay` 做置灰说明。

### 11.5 退款字段拼装规则（C-04 裁决，已落进类型注释 + 可执行函数）

后端 `POST /order/applyRefund` 只接 `{ id, reason }`，`reason` 校验 `max:255`。因此：

```
reason = 原因标签 + （有补充说明时）'：' + 补充说明
例：'行程变更：婚礼改到明年，已与顾问沟通过'
```

- 表单只有 **「退款原因（单选）」+「补充说明（选填）」**；
- **不出现可退金额输入框**（服务端算）；
- **不出现凭证上传**（接口不收 `images`，要留证据只能引导人工客服）；
- 长度由 `buildRefundReason()` 兜底截断（优先保留原因标签）；
- 金额只读展示，来源只有 `getRefundDetail().refund_amount` 或订单详情 `refundable_amount`，**拿不到就不展示**；
- 可退资格读订单详情 `can_user_refund` + `refundable_amount`，不要在页面重算状态组合。

### 11.9 ⚠ 风险登记：下单不占位（对应 UX 硬伤 X8，需立产品/后端工单）

**结论：`order/create` 不占位、不锁档；档期锁定发生在首笔实收之后。**

证据（`server/app/api/logic/OrderLogic.php`）：
- 创建订单只调 `ensureScheduleAvailable()` → `Schedule::checkAvailabilityForUserWithReason()`，**纯校验**；
- 订单项写死 `'schedule_id' => 0`、`'schedule_date' => $date`，不写 schedule 记录；
- 业务规则「首笔实收后锁档」（`docs/业务状态与接口.md:23`）；
- `pay_deadline_time` 是**「待支付」阶段的自动取消截止**（`transaction.cancel_unpaid_orders`，`cancel_unpaid_orders_times` 默认 30 分钟），只在 `order_status=1 且首次待支付阶段` 下发（`shouldDisplayPayCountdown()`），超时 `syncExpiredAutoCancel()` → 取消并释放。

**时序错位（设计稿 vs 系统）**：

| 设计稿 | 系统实际 |
|---|---|
| 08 订单确认页：「已锁档」角标 + 「订单为你保留 30 分钟」 | 订单尚未创建，**未占任何档期**；`pay_deadline_time` 此时不存在 |
| 09 支付成功 | 首笔实收后**才**锁档 |
| 10 / 22 待支付卡「剩余 28:41」 | 这里才是真实 30 分钟窗口（`pay_deadline_time`） |

**风险**：下单 → 商家确认 → 首笔实收 之间存在窗口，档期可能被他人抢走，出现「付了钱没档期」。
**这不是 UI 能修的**，需要在产品/后端层面做「下单即占位 + 超时释放」。

**前端在本轮的口径（已与 UX 对齐）**：
1. 08 屏删「已锁档」角标与 30 分钟承诺，文案改「提交后由主持人确认档期」；
2. 09 屏若展示倒计时，用 `pay_deadline_time`，且只在 `order_status=1` 时显示；
3. 08 提交前建议再调一次 `checkAvailable({staff_id, date})` 做二次校验（降低概率，不消除）；
4. **不得用文案掩盖**，需主理人立工单跟踪。
