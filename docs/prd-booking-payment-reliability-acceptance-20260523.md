# PRD / Acceptance: 预约、支付、档期核心可靠性与产品闭环

Date: 2026-05-23
Owner: 产品经理
Status: 本轮整改验收口径，供研发自测、QA 回归、上线试运营评审使用
Scope: 小程序消费者链路、PC 导流、后台运营处理、支付回调、档期锁、问卷、CRM 线索闭环

## 1. 业务目标

1. **预约可靠**：同一服务人员/套餐/日期/时段在高并发下只能被一个有效订单占用；锁定、下单、取消、过期释放必须可解释、可恢复、可追踪。
2. **支付可靠**：只有通过金额、订单状态、第三方交易号、支付者身份校验的支付回调才能推进订单；重复回调、取消后回调、异常支付不能造成重复入账、重复通知、订单复活或档期误占。
3. **关键失败态可恢复**：人员详情、订单详情、支付结果、确认函、问卷、通知等关键页面在接口失败、鉴权失效、数据不存在、状态过期时必须有页面级错误态、重试和返回路径。
4. **客户主线贯通**：咨询、预约、问卷、订单、支付、售后、评价、CRM 跟进要能归到同一客户视图，支持运营判断客户阶段和下一步动作。
5. **转化和履约闭环**：PC 流量能明确导入小程序预约；支付后用户能在订单详情进入改期、加项、售后、评价、问卷、确认函；后台能处理并回传状态。

## 2. 核心用户场景

- 用户从 PC 首页或内容页了解服务，扫码/点击进入小程序，浏览服务人员详情，查看档期并发起预约。
- 用户在预约锁倒计时内提交订单并支付；支付成功后看到订单状态、确认函、后续履约说明和订阅提醒。
- 两位用户同时抢同一档期时，只有一位用户下单/支付成功，另一位用户得到明确失败原因并可重新选择档期。
- 支付平台重复推送、金额不一致、交易号重复、payer 不一致、订单已取消后才回调时，系统不误改订单并给后台留下处理线索。
- 服务人员/运营人员推送新人问卷，用户填写一次后历史答案可追溯；后续模板升级不污染已发任务和已提交答案。
- 用户支付后需要改期、暂停、加项、售后、评价、回访时，从订单详情能找到入口，后台能处理并通知用户。

## 3. 成功指标与上线试运营门槛

### 3.1 P0 硬门槛

- 并发抢同一档期的重复成功订单数为 **0**。
- 支付回调金额/订单号/状态/transaction_id/payer 任一关键校验失败时，订单不得进入已支付或待服务状态。
- 同一支付流水的重复成功回调不得重复增加 `paid_amount`、重复生成资金流水、重复通知、重复锁档。
- 取消/超时关闭后的支付回调不得复活订单，不得重新占用档期；如已实际收款，必须进入异常支付/退款补偿链路。
- 人员详情、订单详情、支付结果、确认函关键失败态均具备“重试 + 返回上一页/订单列表 + 联系顾问或重新选择”的恢复路径。

### 3.2 P1/P2 试运营指标

- PC 首屏、服务/套餐模块、联系区至少各有一个明确小程序预约 CTA 或二维码入口。
- 小程序订阅状态在订单详情/消息中心有解释和补订入口；用户拒绝订阅后仍能继续主流程。
- 问卷任务创建、推送、填写、查看后台闭环可跑通；模板版本升级不影响历史任务。
- 订单详情按订单状态展示改期/加项/暂停/售后/评价/问卷/确认函入口；无权限或不可用时解释原因。
- CRM 客户视图可从 `user_id` 或绑定手机号关联到咨询、订单、问卷、售后、评价记录。

## 4. 统一客户主键产品口径

### 4.1 主键定义

- **消费者业务主键：`user_id`**。小程序登录用户、订单、支付、问卷、售后、评价、收藏、通知订阅均以 `user_id` 作为首要关联键。
- **CRM 客户主键：`customer_id`**。CRM 跟进、分配、流失预警等运营对象使用 `customer_id`；当用户已登录或手机号已验证时，CRM 客户必须绑定对应 `user_id`。
- **授权身份：openid/unionid**。微信 openid、unionid 仅作为登录/支付校验身份，不作为业务客户主键；支付回调中的 payer openid 必须反查到支付记录所属 `user_id`。
- **订单主键：`order_id/order_sn`**。用于履约、支付、售后、问卷任务的业务单据关联，不替代客户主键。

### 4.2 贯通规则

| 触点 | 必填关联 | 产品要求 |
| --- | --- | --- |
| 游客咨询/PC 留资 | 手机号、来源渠道；有登录态时带 `user_id` | 未登录线索先建 CRM 客户；用户后续登录或验证手机号后合并/绑定到同一 `customer_id`。 |
| 预约/订单 | `user_id`、`order_id`、服务人员/档期 | 订单创建后不得变更归属用户；后台仅能补充顾问信息，不能改写订单用户。 |
| 支付/退款 | `payment_sn`、`order_id`、`user_id`、`transaction_id` | payer 校验必须回到支付记录所属用户；退款也必须沿用订单用户。 |
| 新人问卷 | `task_id`、`order_id`、`user_id`、`staff_id`、`version_id` | 问卷任务归属订单与客户，历史答案可从订单和客户视角查看。 |
| 售后/改期/评价 | `order_id`、`user_id` | 所有申请和评价均可回到订单详情与 CRM 客户视图。 |
| CRM 跟进 | `customer_id`，尽量带 `user_id` | 运营跟进时展示咨询、订单、问卷、售后、评价摘要。 |

### 4.3 合并与冲突规则

1. 绑定优先级：`user_id` 精确匹配 > 已验证手机号匹配 > 人工确认合并。
2. 同手机号多个 `user_id`、同 `user_id` 多个 CRM 客户、openid 与订单用户不一致均视为异常，需要进入后台人工核查，不允许自动覆盖已支付订单归属。
3. 合并客户时保留所有订单、支付、问卷、售后、评价历史；CRM 跟进记录迁移到保留的 `customer_id`，并记录合并日志。
4. 线索来源必须保留首触来源和最近来源，PC 导流建议写入 `source_channel=pc_*`，方便评估转化。

### 4.4 验收标准

- 给一个已登录用户从 PC 留资、预约下单、填写问卷、提交售后、发表评价后，后台可在同一客户视图查看完整轨迹。
- 未登录 PC 留资后，用户用同一手机号登录小程序下单，CRM 不产生不可解释的重复客户；如产生重复，后台有合并入口和风险提示。
- 支付回调 payer openid 不属于订单用户时，支付不成功入账，订单不推进，并留下拒绝原因。

## 5. 问卷模板版本化与重复提交规则

### 5.1 产品规则

1. 问卷配置支持草稿与发布版本：编辑草稿不影响已发布版本；点击发布后生成新的 `version_no/version_id`。
2. 新建问卷任务使用当时的当前发布版本，并将标题、描述、题目写入任务快照。
3. 已发任务不随模板后续编辑/发布变化；用户看到和提交的始终是任务快照。
4. 一个订单默认只能有一个新人问卷任务；若确需重发，应复用原任务进行提醒，或由运营明确取消旧任务后创建新任务，不能静默生成多个待填任务。
5. 一个任务只允许成功提交一次。重复点击提交、网络重试、刷新后再次提交，不得覆盖首个有效答案；页面提示“已提交，可查看历史答案”。
6. 历史答案保留 `task_id/order_id/user_id/staff_id/version_id/version_no/questions_snapshot/answers/create_time`，供小程序与后台查看。

### 5.2 验收标准

- 发布 v1 问卷并发送给订单 A；随后编辑草稿并发布 v2。订单 A 继续展示 v1 内容，新订单 B 展示 v2 内容。
- 用户对同一任务连续点击提交两次：仅产生一份答案，任务状态为已填写，第二次返回已提交提示，不覆盖答案。
- 后台任务列表可筛选待填写/已填写/已取消；任务详情可查看版本号、题目快照、答案、提交时间、订单与客户信息。
- 删除/禁用题库题目不影响历史问卷任务和答案展示。
- 发送失败、用户未订阅或消息不可达时，任务仍保留在小程序“新人问卷”列表与订单详情提示中，用户可主动进入填写。

## 6. 小程序订阅补订、状态解释与失败恢复

### 6.1 订阅场景

优先覆盖以下场景：订单确认/支付成功、确认函更新、问卷待填写、改期/暂停/加项处理结果、售后工单进度、退款结果、评价/回访问卷提醒。

### 6.2 状态文案建议

| 状态 | 用户文案 | 可用动作 |
| --- | --- | --- |
| 未订阅 | “开启提醒后，我们会在订单确认、确认函更新、售后进度变化时通知你。” | 去订阅、暂不订阅 |
| 已订阅 | “已开启本订单关键提醒。” | 查看消息中心 |
| 用户拒绝 | “你暂未开启提醒，仍可在订单详情查看最新进度。” | 重新订阅、知道了 |
| 系统限制/模板不可用 | “提醒暂时不可用，不影响订单处理。” | 稍后重试、返回订单 |
| 发送失败 | “提醒发送失败，但事项已记录。” | 查看订单/问卷/工单详情 |

### 6.3 验收标准

- 用户拒绝订阅不阻塞支付、退款、提交工单、提交问卷等主动作。
- 订单详情和消息中心至少提供一次补订入口；补订失败时显示原因和“稍后重试/返回订单”。
- 通知跳转确认函时，如通知携带版本已失效，应提示“确认函版本已更新”，并引导查看当前订单详情/当前有效确认函。
- 消息中心为空、加载失败、无权限时均有空态/错误态和返回路径。

## 7. PC 小程序导流与预约转化 CTA

### 7.1 入口要求

PC 端不要求完整下单闭环，但必须承担外部流量转化：

- 首页首屏：展示“立即预约 / 扫码进入小程序预约 / 查看档期”之一，优先绑定小程序二维码。
- 服务/套餐/人员卡片：每个高意向内容区提供“预约咨询 / 查看档期 / 扫码预约”动作。
- 联系区：展示电话、服务时间、地址、小程序二维码；二维码缺失时展示“请联系管理员配置小程序码”兜底，不只显示空白。
- 内容/动态页：在文章尾部或侧栏保留小程序预约 CTA。

### 7.2 埋点/线索口径

- PC 导流建议按位置写入来源：`pc_home_hero`、`pc_service_card`、`pc_package_card`、`pc_contact_qr`、`pc_article_cta`。
- 用户扫码进入小程序后，若完成咨询/预约，应在 CRM 首触或最近来源中可见 PC 来源。

### 7.3 验收标准

- 桌面和移动浏览器下，首屏不滚动即可看到至少一个预约 CTA。
- 二维码加载失败时有文本兜底和电话咨询路径。
- 从 PC CTA 到小程序预约页/人员详情页的路径可被测试人员复现，并能在 CRM/订单来源中追踪。

## 8. 售后、改期、评价入口与后台处理闭环

### 8.1 小程序订单详情入口矩阵

| 订单状态 | 应展示/可解释入口 |
| --- | --- |
| 待确认 | 查看预约信息、联系顾问、取消/返回列表；说明确认倒计时和超时处理。 |
| 待支付 | 支付/上传线下凭证、取消订单、联系顾问；说明支付倒计时和失败恢复。 |
| 已支付/待服务 | 确认函、新人问卷、申请改期、申请加项、申请暂停、售后咨询/工单、联系顾问。 |
| 服务中 | 售后工单、联系顾问、确认完成；按业务规则决定是否允许改期/加项。 |
| 已完成 | 评价、回访问卷、售后工单、查看确认函/订单归档、再次预约。 |
| 已评价 | 查看评价、售后工单、再次预约。 |
| 已取消/已退款 | 查看处理记录、退款/异常支付说明、再次预约；不可展示会造成误操作的支付/改期入口。 |
| 已暂停 | 暂停详情、恢复/继续沟通入口、售后工单、联系顾问。 |

### 8.2 后台处理闭环

- 改期/暂停/加项：后台能查看申请、原订单信息、客户信息、原因与附件；处理时必须填写同意/拒绝原因；通过后更新订单/档期/加项状态并通知用户。
- 售后工单/投诉：后台能分配处理人、更新进度、追加回复、完成/关闭；用户端能查看进度和回复。
- 评价/回访：用户完成评价后订单进入已评价或保留评价状态；后台可查看、审核/回复/沉淀到人员服务质量指标。
- 问卷：后台能从订单或人员视角查看问卷任务和答案，服务人员可用于履约准备。

### 8.3 验收标准

- 对每个订单状态抽样进入订单详情，入口展示符合矩阵；不可用入口必须有原因，不允许按钮点击后只报通用失败。
- 后台处理改期/售后后，小程序订单详情和消息中心能刷新到最新状态。
- 用户提交售后/改期/评价后，可从订单详情回到对应详情页，且后台列表能检索到同一记录。

## 9. P0 预约锁、支付失败与回调验收场景

| ID | 场景 | 前置条件 | 操作 | 预期结果 |
| --- | --- | --- | --- | --- |
| P0-LOCK-01 | 并发抢同一档期 | 同一人员/套餐/日期/时段可预约 | 两个用户同时提交预约/下单 | 仅一个订单成功；失败用户看到“档期已被占用/请重新选择”；无重复确认档期。 |
| P0-LOCK-02 | 锁倒计时到期 | 用户已临时锁定档期但未提交订单 | 等待倒计时归零后点击提交 | 提交被阻止或服务端拒绝；页面提示锁已过期，提供重新锁定/重新选择。 |
| P0-LOCK-03 | 下单事务失败释放 | 下单过程中模拟订单项/支付单创建失败 | 提交订单 | 订单不半生成，档期锁不永久占用，用户可重试。 |
| P0-LOCK-04 | 取消未支付释放 | 订单待支付且占用临时/待确认档期 | 用户取消订单或支付超时 | 订单变取消/关闭；档期按规则释放；原用户和其他用户看到一致可预约状态。 |
| P0-PAY-01 | 正常微信回调 | 待支付订单、金额和 payer 正确 | 推送 SUCCESS 回调 | 支付记录已支付，订单推进，资金流水一次，通知一次，首笔支付后档期正式锁定。 |
| P0-PAY-02 | 金额不一致 | 支付记录应付金额为 A | 回调 total != A | 支付不成功，订单不推进，记录拒绝原因，用户仍可重试/联系顾问。 |
| P0-PAY-03 | 商户单号不匹配 | 已有 payment_sn | 回调 out_trade_no 为其他值 | 拒绝回调，不改变订单支付状态。 |
| P0-PAY-04 | transaction_id 复用 | 另一支付记录已使用该交易号 | 新回调使用相同 transaction_id | 拒绝处理，不重复入账。 |
| P0-PAY-05 | payer 不一致 | 回调 openid 不属于订单用户 | 推送成功支付回调 | 拒绝处理，订单不推进，记录身份不一致原因。 |
| P0-PAY-06 | 重复成功回调 | 首次回调已成功处理 | 再次推送相同 payment_sn + transaction_id + payer + amount | 返回已处理或幂等成功；不重复累计金额、资金流水、通知、锁档。 |
| P0-PAY-07 | 重复回调但交易号不同 | 支付记录已支付 | 再推不同 transaction_id | 拒绝重复回调，记录 replay reject，不覆盖原成功流水。 |
| P0-PAY-08 | 取消后收到成功回调 | 订单已取消/超时关闭 | 推送真实成功支付回调 | 订单不复活；不重新占档；支付登记异常；符合条件时创建系统退款/补偿处理记录。 |
| P0-PAY-09 | 首笔支付后锁档失败 | 支付成功但正式锁档失败 | 模拟锁档条件冲突 | 不展示为健康已支付履约；登记异常支付，生成退款/人工处理线索，确认函失效。 |
| P0-PAGE-01 | 支付结果未知 | 支付后结果页查询失败/超时 | 打开支付结果页 | 页面展示未知/查询失败态，提供重新查询、返回订单详情、重新支付（若仍待支付）。 |
| P0-PAGE-02 | 确认函版本失效 | 通知带旧 letter_id | 点击通知 | 提示版本已更新，引导订单详情查看当前有效确认函。 |

## 10. 关键页面错误态验收清单

| 页面 | 错误场景 | 必备恢复路径 |

| 订单确认 `/packages/pages/order_confirm/order_confirm` | 锁过期、价格变化、套餐/加项不可用、提交失败 | 刷新价格/重新锁定、返回预约页、联系客服；不得静默提交旧数据。 |

| 支付结果 `/pages/payment_result/payment_result` | 支付失败、取消支付、结果未知、查询超时 | 再次查询、继续支付、返回订单详情、联系顾问。 |

## 11. 用户故事与验收标准

### P0 用户故事

1. 作为准备预约婚礼服务的用户，我希望锁定档期后看到剩余时间和失效处理，以便在有效时间内完成下单。
   - 验收：锁倒计时可见；倒计时结束后不能提交旧锁；提供重新选择/重新锁定。
2. 作为支付用户，我希望支付失败或结果未知时能回到订单继续处理，而不是丢失订单。
   - 验收：支付结果页有查询、重试、返回订单；订单详情能展示当前待支付/已支付/异常状态。
3. 作为平台运营，我希望异常支付回调不会误改订单，以便资金和档期安全。
   - 验收：金额、状态、transaction_id、payer、取消后回调均按 P0 场景通过。

### P1 用户故事

1. 作为运营顾问，我希望从同一客户视图看到咨询、预约、问卷、售后、评价，以便判断客户阶段。
2. 作为新人，我希望订阅提醒失败后仍能在订单详情找到待办事项，以免错过确认函、问卷或售后进展。
3. 作为 PC 访客，我希望看到明确扫码预约入口，以便从官网快速进入小程序下单。
4. 作为已下单用户，我希望从订单详情直接申请改期、加项、售后和评价，以便自助完成履约后链路。

### P2 用户故事

1. 作为维护人员，我希望关键失败态、空态和按钮文案统一，降低后续页面维护成本。
2. 作为业务负责人，我希望能按 PC 来源、订阅状态、问卷填写率、售后处理时效观察试运营效果。

## 12. 优先级落地建议

### P0 必须上线前通过

- 支付回调校验与幂等：金额、订单状态、transaction_id、payer、重复回调、取消后回调。
- 档期锁与订单生成：事务/行锁/条件更新，并发抢档、锁过期、取消释放。
- 关键失败态：人员详情、订单确认、订单详情、支付结果、确认函。

### P1 试运营首周必须补齐

- 统一客户主键和 CRM 贯通口径。
- 问卷模板版本化、重复提交、历史查看。
- 订阅补订和状态解释。
- PC 导流 CTA 与来源追踪。
- 订单详情售后/改期/加项/评价/问卷入口与后台处理闭环。

### P2 持续优化

- 统一 EmptyState/ErrorState/Skeleton、字段级错误、toast 文案规范。
- 建立运营指标看板：预约转化、锁过期率、支付失败恢复率、订阅授权率、问卷完成率、售后响应时效。
- 梳理后台权限/菜单健康检查和页面拆分，降低运营误操作和维护风险。

## 13. 风险清单

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| `user_id` 与 `customer_id` 绑定不一致 | CRM 看不到完整客户轨迹，可能重复跟进 | 上线前抽样检查订单客户、问卷客户、CRM 客户映射；提供合并规则。 |
| 支付异常补偿链路无人处理 | 用户已扣款但订单未推进，投诉风险高 | 异常支付必须进入后台待处理/退款列表，并有通知或每日巡检。 |
| 订阅模板配置缺失 | 用户收不到关键提醒 | 主流程不依赖订阅；消息中心和订单详情保留待办入口。 |
| 问卷版本快照缺失 | 历史答案无法解释 | 任务和答案必须保存题目快照，不只引用当前模板。 |
| PC CTA 只展示二维码但不可追踪 | 无法判断投放转化 | 增加来源参数和 CRM/订单来源落点。 |
| 订单详情入口过多但状态规则不清 | 用户误操作或后台处理压力上升 | 按订单状态矩阵控制入口，禁用时解释原因。 |
| 并发测试只测单接口不测完整链路 | 上线后仍可能重复占档 | QA 需覆盖锁定、下单、支付首笔锁档、取消释放全链路。 |

## 14. 上线试运营判定

可以进入试运营的最低条件：

1. P0 验收场景全部通过，且有 QA 记录或自动化测试证据。
2. P1 中客户主键、问卷、订阅、PC CTA、售后/改期/评价入口至少完成主路径并可人工验证。
3. 后台存在异常支付、售后工单、问卷任务、改期/加项申请的处理入口或明确人工处理 SOP。
4. 关键页面失败态不再只有 toast 或空白页，用户能明确下一步。
5. 试运营期间建立每日巡检：重复订单、异常支付、退款待处理、问卷未推送/未填写、售后超时、PC 来源转化。
