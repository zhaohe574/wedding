# 核心状态机与流转约束

本文约束预约、订单、支付、档期、问卷核心可靠性。代码辅助来源：`server/app/common/contract/CoreStateContract.php`。

## 1. 订单状态

| 值 | 常量 | 含义 | 允许下一状态 |
| --- | --- | --- | --- |
| 0 | `STATUS_PENDING_CONFIRM` | 待服务人员/管理员确认 | 1 待支付、6 已取消 |
| 1 | `STATUS_PENDING_PAY` | 待用户支付 | 2 待服务、6 已取消、10 退款中、8 已退款 |
| 2 | `STATUS_PENDING_SERVICE` | 已支付，待服务 | 3 服务中、4 已完成、7 已暂停、10 退款中、8 已退款、6 已取消 |
| 3 | `STATUS_IN_SERVICE` | 服务中 | 4 已完成、7 已暂停、10 退款中 |
| 4 | `STATUS_COMPLETED` | 已完成 | 5 已评价、10 退款中 |
| 5 | `STATUS_REVIEWED` | 已评价 | 10 退款中 |
| 6 | `STATUS_CANCELLED` | 已取消 | 稳定态；仅异常支付补偿/人工处理可关联退款，不回退状态 |
| 7 | `STATUS_PAUSED` | 已暂停 | 2 待服务、3 服务中、6 已取消、10 退款中 |
| 8 | `STATUS_REFUNDED` | 已退款 | 稳定态 |
| 9 | `STATUS_USER_DELETED` | 用户已删除 | 稳定态 |
| 10 | `STATUS_REFUNDING` | 退款中 | 8 已退款、2 待服务、4 已完成 |

关键约束：

- 支付回调只允许把 `待支付` 订单推进到已支付后的服务态；订单已取消/已关闭后收到回调，应登记异常支付并触发补偿/退款流程，不直接恢复订单。
- 订单状态推进必须记录 `la_order_log`，并在日志/响应中可用 `request_id` 关联。
- 自动取消、确认超时、尾款超时属于系统操作，必须保持幂等，多次执行不得重复释放或重复通知。

## 2. 支付流水状态

| 值 | 含义 | 允许下一状态 |
| --- | --- | --- |
| 0 | 待支付 | 1 已支付、3 支付失败 |
| 1 | 已支付 | 2 已退款 |
| 2 | 已退款 | 稳定态 |
| 3 | 支付失败 | 稳定态 |

支付回调校验清单：

1. SDK/渠道签名校验必须先通过。
2. `payment_sn/out_trade_no` 必须命中本地待处理支付流水。
3. 回调金额和本地 `pay_amount` 必须一致，币种仅允许 CNY。
4. `transaction_id` 必须非空；重复回调 transaction_id 不一致需记录异常并拒绝或人工处理。
5. `payer/openid` 必须与发起支付时的用户/渠道身份一致；当前代码已具备金额校验，若新增 payer 字段持久化，应按本条补齐强校验。
6. 本地订单必须存在且处于 `待支付`；取消后/超时后回调进入异常支付补偿，不重复推进订单。
7. 重复回调必须幂等：不得重复累加 `paid_amount`、不得重复生成资金流水、不得重复通知。

## 3. 档期状态

| 值 | 含义 | 允许下一状态 |
| --- | --- | --- |
| 0 | 不可用 | 1 可预约、4 内部预留 |
| 1 | 可预约 | 3 已锁定、2 已预约、0 不可用、4 内部预留 |
| 2 | 已预约 | 1 可预约、0 不可用 |
| 3 | 已锁定 | 1 可预约、2 已预约 |
| 4 | 内部预留 | 1 可预约、0 不可用、2 已预约 |

档期锁定要求：

- 锁定使用 Redis 锁协调 + 数据库条件更新/行锁，避免并发抢档双成功。
- 同一用户重复锁定同一档期可续期；不同用户抢占必须失败并返回可恢复错误。
- 前端倒计时以 `lock_expire_time` 为准，倒计时结束后不可继续提交订单，应重新校验或重新锁定。
- 订单创建失败时必须释放本次锁；支付成功首笔锁定失败需登记异常支付并触发退款补偿。
- 取消待确认/待支付订单应释放未转为已预约的锁；已支付后释放需走退款/改期等业务流程。

## 4. 订单项状态

| 值 | 含义 | 允许下一状态 |
| --- | --- | --- |
| 0 | 待服务 | 1 服务中、2 已完成、3 已取消 |
| 1 | 服务中 | 2 已完成、3 已取消 |
| 2 | 已完成 | 稳定态 |
| 3 | 已取消 | 稳定态 |

订单项确认状态 `confirm_status` 与服务状态分离：服务人员确认只推进确认维度；全部有效项确认后整单进入待支付。

## 5. 新人问卷任务状态

| 值 | 含义 | 允许下一状态 |
| --- | --- | --- |
| 0 | 待提交 | 3 已查看、1 已提交、2 已取消、4 已过期 |
| 1 | 已提交 | 稳定态 |
| 2 | 已取消 | 稳定态 |
| 3 | 已查看 | 1 已提交、2 已取消、4 已过期 |
| 4 | 已过期 | 稳定态 |

配套状态：

| 状态域 | 值 | 含义 | 允许变化 |
| --- | --- | --- | --- |
| 问卷配置 `status` | 0 | 停用 | 1 启用 |
| 问卷配置 `status` | 1 | 启用 | 0 停用 |
| 推送方式 `push_mode` | 1 | 自动推送 | 2 手动触发 |
| 推送方式 `push_mode` | 2 | 手动触发 | 1 自动推送 |
| 任务发送 `send_status` | 0 | 待推送 | 3 推送中、1 已推送、2 推送失败 |
| 任务发送 `send_status` | 1 | 已推送 | 3 推送中；允许重发提醒但不得生成新任务 |
| 任务发送 `send_status` | 2 | 推送失败 | 3 推送中、1 已推送 |
| 任务发送 `send_status` | 3 | 推送中 | 1 已推送、2 推送失败 |
| 题库题目 `status` | 0 | 禁用 | 1 启用 |
| 题库题目 `status` | 1 | 启用 | 0 禁用 |

问卷治理要求：

- 服务人员按订单发送问卷时必须校验订单、客户、服务人员绑定；一个订单默认只存在一个问卷任务。
- 用户提交时必须校验任务归属、已发送/推送失败可见状态、任务状态、过期时间和题目版本快照；通知推送失败不阻塞用户主动填写。
- 已提交任务重复提交可幂等返回成功但不得覆盖历史答案；已取消和已过期任务不可提交。
- 问卷配置发布产生版本快照；任务创建时冻结题目快照，历史任务不得被草稿编辑或新版发布影响。
- 任务创建幂等键为 `order_id`；答案提交幂等键为 `task_id`；发布版本幂等边界为单次事务内的 `questionnaire_id + version_no`。
- 手动发送仅允许 `status ∈ {待提交, 已查看}` 且未过期的任务；已提交/已取消/已过期任务不得发送。重复发送可更新 `last_send_time/send_count`，但站内信必须按目标去重。
- 用户端列表/详情/提交必须限制 `user_id` 和 `send_status = 已推送`；管理员查看全部任务，服务人员端只能查看 `staff_id` 归属任务。
- 后台草稿保存、发布、发送、题库变更必须进入后台操作日志；日志上下文至少包含 `request_id/admin_id/path`，涉及任务时补 `task_id/order_id/staff_id`。
- 用户提交失败、重复提交、必填缺失必须在响应体和响应头返回同一个 `request_id`，便于客服按 `request_id + task_id` 排查。
- 现有实现为“创建时冻结任务快照”：任务创建时写入 `version_id/version_no/questions_snapshot/expire_time`；提交后答案表再保存同一题目快照。发布新版不得批量改写既有任务。

推荐错误码（统一 Envelope 的 `code` 仍使用 `0` 表示业务失败，以下放入 `data.error_code`）：

| error_code | 场景 | 前端处理 |
| --- | --- | --- |
| `QUESTIONNAIRE_NOT_FOUND` | 任务不存在、未发送或无权限 | 返回任务列表/订单详情，展示 `request_id`。 |
| `QUESTIONNAIRE_ALREADY_SUBMITTED` | 已提交任务再次提交但接口选择返回失败时 | 展示已提交态，提供查看答案/返回路径；当前实现可直接幂等成功。 |
| `QUESTIONNAIRE_CANCELLED` | 任务已取消 | 禁止填写，返回订单详情。 |
| `QUESTIONNAIRE_EXPIRED` | 任务已过期 | 禁止填写，提示联系服务人员重发。 |
| `QUESTIONNAIRE_VERSION_MISSING` | 发布版本或题目快照缺失 | 提示联系服务人员/客服，允许重试。 |
| `QUESTIONNAIRE_REQUIRED_MISSING` | 必填答案缺失 | 定位题目并保留本地输入。 |
| `QUESTIONNAIRE_SEND_NOT_ALLOWED` | 非待提交/已查看或已过期任务发送 | 后台刷新任务详情。 |
| `QUESTIONNAIRE_TEMPLATE_INVALID` | 题库/草稿题目不合法 | 后台表单定位错误题目。 |
| `QUESTIONNAIRE_SEND_FAILED` | 站内信写入失败或用户/任务数据缺失 | 后台显示失败原因和下次重试时间。 |

## 6. 高风险变更备选与回滚

| 变更 | 风险 | 备选/回滚 |
| --- | --- | --- |
| 强制启用显式路由 | 自动路由接口可能失效 | 先只为核心接口补 OpenAPI 和灰度路由；异常时回滚路由配置，保留控制器。 |
| 支付回调新增 payer 持久化强校验 | 旧支付流水缺少 payer 快照 | 先增加 nullable 字段与新单写入，旧单仅记录 warning；稳定后再强制。 |
| 操作日志新增独立 request_id 字段 | 老库未迁移会写入失败 | 当前先写入 `params.__context`；完成迁移后再模型显式字段化。 |
| 拆分超大页面/服务 | 容易引入回归 | 先抽纯函数/只读组件和文档边界，保留原入口；失败可单文件回退。 |
| 问卷创建时冻结 | 服务人员发布新版无法自动修正已创建任务 | 保持显式取消/过期旧任务再创建新任务；如需回退，仅读取原 `version_id` 对应版本并补写快照，禁止读取最新版本。 |
| 问卷重复提交幂等成功 | 前端可能误以为新答案覆盖成功 | 响应必须展示已提交状态；后端不得更新既有答案，可在详情返回原答案摘要。 |
