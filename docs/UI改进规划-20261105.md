# newuniapp 小程序 UI 改进规划

> 范围：`newuniapp/`（重建版，42 个页面 / 5 个分包 / 9 个基础组件）
> 基线：分支 `codex/ui-upgrade-20261027`，只读代码判定，不含任何代码改动
> 参与评审：交互与信息架构（简宜人）、视觉与设计系统（颜有光）、前端可行性（甄像素）
> 结论口径：本文所有数字均可在仓库内复算；标注「未验证」的项不作为结论使用

---

## 零、一句话结论与三个关键动作

**这套 UI 的骨架比老端好一个量级——token 纪律已经立住，但它是「一张被严格遵守的颜色表」，还不是「能自我约束的设计系统」；更要紧的是交易闭环有三处硬断裂，UI 做得再细，用户也走不到那些界面。**

1. **先修交易闭环（5 项 P0）**，再谈视觉。订单详情 6 个动作没有 UI 出口、预约页提交按钮静默拒绝、支付结果页重付前不查状态——这三条任意一条都足以让整轮 UI 投入失效。
2. **修正图标单位**。`u-icon` 的 `size` 是 rpx 不是 px，全站 89 处图标实际只有标称值的一半（tabbar 图标 11px）。这是「界面看着廉价」最直接的技术根因，改动量极小。
3. **把组件补齐到能承载页面**。现在只有 9 个基础组件，没有 Input / Field / Sheet / Dialog / FilterBar，导致每个页面自己写表单和弹层——规范落不了地，不是执行问题，是缺件。

## 一、现状判断

### 1.1 已经做对的（本轮不要动）

| 项 | 实测 | 说明 |
|---|---|---|
| 色值纪律 | 硬编码 hex **13 处**，`var(--)` 引用 **2056 处** | 老端是 3274 处 hex，这一项进步是数量级的 |
| 字号纪律 | 页面级 `font-size` 仅 1 处裸值 | 全部走 token |
| 分包结构 | 主包 11 页 + 5 个分包 | 42 页仍能压住体积 |
| 单页体量 | 最大 `booking.vue` 997 行 | 老端最大 3302 行，尚未失控但已到临界 |
| 三态意识 | `base-empty` 被 26 个文件调用（45 处） | 组件已存在，缺的是语境化 |

**判断**：这套代码的「可改造性」是好的。真正的问题不在脏，而在**缺件**和**断链**。

### 1.2 五类问题的实测结论

#### ① 视觉一致性：token 立住了，但档位过密、语义有洞

| 问题 | 证据 | 影响 |
|---|---|---|
| **图标整体偏小一半** | `u-icon` 的 `size` 走 `addUnit()`，默认单位 **rpx**（`libs/function/addUnit.js:4`），调用处按 px 直觉传值 | `:size="22"` → 11px；tabbar 图标 11px（常规 24–28px）；`size="12"` 的箭头仅 6px |
| 图标尺寸 16 种取值 | 89 处 `u-icon` 中 `:size` 命中 12(34)、18(12)、22(8)、10(7)、20(6)、13(5)、16(5)、26(2)、28(2)、72(2)，11/14/15/30/32/40 各 1；其余不传 `size` 走默认 32rpx | 无阶梯，靠手感 |
| 字号档位过密 | `fs-xs 22rpx` 被用 **124 次（34.9%）**，22/24/28 三档差值 2–4rpx 视觉不可辨，却吃掉 87.8% | 标题层级没建立，页面靠色块和加粗硬撑 |
| 对比度：1 处硬缺陷 + 1 处临界 | `line-strong` 作控件边界 **1.59:1**（要求 3.0，唯一硬缺陷，输入框与 ghost 按钮边框都用它）；`neutral` on `neutral-bg` **4.48:1**（差 0.02）；`ink-3` 在页面底实测 **4.60:1 达标**，仅在 3 种浅色底上不达标（4.22–4.40，合计 4 处）；`brand` 作正文 2.25:1 属守则问题，实测零处白字压金 | 弱视与强光下输入框边界「消失」；空态图标（1.59:1）几乎不可见 |
| **uview 主题桥接配置错误** | `uni.scss` 用 `theme("colors.*")` 把 30+ 个 `$u-*` 变量接到 `tailwind.config.js`，而后者全部指向 `var(--color-*, …)`——**`--color-*` 在全项目从未被定义**（grep 0 处）。38 个 uview 组件消费这些变量 | `$u-type-primary` 无 fallback → 声明失效、颜色继承；其余回落到 uview 旧色（#666/#333/#19be6b/#ff2c3c/#FFB814）。**整个组件库不在品牌色体系内**，是一类被忽略的视觉不一致 |
| 运行时主题是死链路 | `stores/theme.ts` 生成的 `vars` 被写 3 次、读 **0 次**，变量字符串直接丢弃 | 更危险的是它暗示「主题可配」，下一个人「修好」它就会让整站配色被后台配置覆盖 |
| 卡片双重分层 | `base-card` 同时用 1rpx 描边 + `shadow-card`，而该阴影 `rgba(74,43,24,.04)` 在米白底上肉眼不可见 | 9 处无效样式 |

#### ② 布局与信息层级：单页结构清楚，跨页上下文丢失

- **预约页不显示「为谁、哪天、什么套餐」**（`booking.vue` 模板无 `date` 引用，`:296` 声明、`:364` 进参数）。用户翻三步之后不知道自己在约什么——这是转化链路上最贵的一处信息缺口。
- **筛选条只有 4 个排序**（`staff-list.vue:4-18`），无日期/分类筛选。带参进入后无法改条件，要返回重填，列表位置全丢。
- **首页 hero 560rpx**，在 320px 窄屏上占去近半屏，分类入口被挤到折线下。
- **标题层级只靠字号**，三档标题合计仅 25 次使用（7%），页面靠色块分区。

#### ③ 交互反馈：几乎不存在

| 项 | 实测 |
|---|---|
| `hover-class` | 业务代码仅 **2 个文件**（`base-button.vue`、`about.vue`），其余 34 处全在 `uni_modules` |
| 列表卡 / chip / tab / 菜单项 | 全部裸 `@tap`，按下无任何反馈 |
| tabbar 角标 | 无 badge；`message.vue:97-102` 已取到 `unread.total` 却不用 |
| 支付失败 | `detail.vue:385-389` catch 只上报，无 toast——用户点了没反应 |
| 步骤条 | 3 步结构正确，但第 3 步名为「确认」，实际是表单填写 |

#### ④ 组件规范：只有容器类组件，没有输入类组件

- 现有 9 个：`app-tabbar`、`base-button`、`base-card`、`base-empty`、`base-skeleton`、`nav-bar`、`price`、`section-header`、`status-tag`。
- **缺 `BaseInput` / `BaseField` / `BaseSheet` / `BaseDialog` / `BaseFilterBar`**。后果是**每个页面各写各的表单**：`booking.vue` 内联 `.form__row` + 裸 `<input>`，其它页各有一套 `.field` / `.q` / `.input` 私有类。项目里确实存在 `styles/form.scss`，但**零引用（死文件）**——不存在"两套写法打架"，问题比"打架"更原始：**没有可复用的表单基座**。
- `price` 组件在调用处传 7 档裸字号（26/28/30/32/34/36/48rpx），列表内嵌价 28rpx = 14px，**与正文同号，金额毫无权重**。
- `base-button` 命名与视觉相反：`brand` 是黑底、`primary` 是金底，而 `primary` **全项目 0 处使用**，是死代码。
- **空态有现成解法**：`vk-uview-ui` iconfont 内置 14 个专用空态图标（`empty-order`/`empty-search`/`empty-favor`/`empty-message`/`empty-wifi`/`empty-permission`/`empty-data` 等），而 `base-empty` 已有 `emptyIcon` prop。**不需要画插画**。

#### ⑤ 多端适配与可访问性：基本空白

- `aria-*` / `role` 全项目命中 **0 处**。
- `base-button` md 档高 **80rpx（40px）**，低于 44×44px 触控标准；sm 档靠 `::before` 撑到 88rpx，说明作者知道热区问题，但只在最小档做了。
- 安全区只在 `page-wrap` 与 `app-tabbar` 处理，`booking.vue` 的 fixed 底栏无 `cursor-spacing`，**键盘遮挡未验证**。
- H5 侧：`pages.json:293-295` 全局 `h5.navigationStyle: "custom"`，而 `:9-11`、`:57-60` 又写 `navigationBarTitleText`，是否冲突**未验证**。
- 图片裁切：`aspectFill` 29 处、`widthFix` 2、`aspectFit` 1、**`scaleToFill` 1（会变形，应禁）**。

### 1.3 横切问题：交易闭环断裂（优先级高于以上全部）

| 编号 | 位置 | 现象 | 后果 |
|---|---|---|---|
| P0-1 | `pkg-order/pages/detail/detail.vue:201-213` / `:219-221` / `:136-165` | `actions` 定义 10 项，`hasMoreActions` 只放行 3 项，模板只渲染 4 项。`apply_refund`/`confirm_complete`/`review`/`fill_questionnaire`/`upload_voucher`/`delete` **无 UI 出口** | 售后闭环断裂，用户只能打客服 |
| P0-2 | `booking.vue:201` + `:325-330` + `:496-500`；`base-button.vue:58` | `:disabled="!canSubmit"`，解释文案写在 `handleSubmit` 内；`disabled` 时该函数不执行 | 灰按钮 + 零解释，像页面卡死 |
| P0-3 | `booking.vue:490-493` / `:502-512` | 报价失败只写 `validations`；`canSubmit` 不含金额；`if (quoteHash.value)` 为空则不传 `quote_hash` 照常下单 | **金额未确认也能下单** |
| P0-4 | `payment-result.vue:21` / `:106-119` / `:39` | fail 态「重新支付」直接 `prepay` 再拉起，**未先查真实支付状态**；轮询 6 次共 32 秒即判 fail | **可能重复扣款** |
| P0-5 | `detail.vue:385-389` | `handlePay` catch 只 `report`，无 toast | 订单过期时点「去支付」毫无反应 |

## 二、改进方向与优先级

| 优先级 | 方向 | 具体项 | 依据 |
|---|---|---|---|
| **P0** | 交易闭环 | 上述 5 项 | 影响下单与资金，UI 投入的前提 |
| **P0** | 可访问性硬伤 | 对比度硬缺陷修复（1 组值 + 5 处局部）、图标单位纠错、md 按钮 80→88rpx | 低成本、全站受益、属"不可辩解"缺陷 |
| **P1** | 交互反馈 | 全站按下态（约 40 处）、失败必 toast、tabbar 角标、步骤条改名 | 成本最低、感知最强 |
| **P1** | 组件规范 | `BaseInput`/`BaseField` 落地、`base-empty` 加 `errorKind`、`price` 收敛 4 档、`base-button` 变体改名 | 规范能否执行的物理前提 |
| **P1** | 布局与层级 | 预约页上下文摘要条、`staff-list` 吸顶筛选条、列表滚动位置保留、hero 高度 | 直接作用于转化率 |
| **P2** | 视觉一致性 | 字号 8→6 档、圆角删死档、间距补 96rpx 分区档、卡片去阴影改描边、图标阶梯 16→6 值 | 回归面 169 处，必须单独批次 |
| **P2** | 多端与可访问性 | H5 导航冲突验证、键盘遮挡、`aria-label` 关键控件、`scaleToFill` 禁用 | 部分需真机，先验证后动手 |

| **P3** | 资产清理 | 9 个零引用 PNG（28.9KB）、删除运行时主题死链路 | 收益有限，但能消除"假可配置" |

## 三、分阶段实施计划

> 人天按「1 名熟悉该代码库的前端」估算，来自前端可行性评估；不含设计、联调与真机回归的人力。
> 关键路径：**阶段一 → 阶段二（组件）→ 阶段三（视觉）**，阶段四可与阶段三并行。

### 阶段一：止血与基线（1.5 周 / 约 10.5 人天）

**目标**：让交易链路能走通，并把"不可辩解的缺陷"清掉。本阶段不追求好看。

**范围**
- 页面：`pkg-order/detail`、`pkg-catalog/booking`、`pkg-order/payment-result`、`pages/order`、`pages/login`
- 全局：`tokens.css`（对比度 4 组）、`base-button`（高度与变体命名）、89 处图标尺寸

**产出**
1. 5 项 P0 修复：P0-1 按 D1 改为**收窄契约**（`OrderActions` 11→5、删 3 个零引用 API、清未用 import），P0-2/P0-3/P0-5 按原方案，P0-4 按 D2 方案 A 落地（需后端先确认 `payStatus` 幂等与延迟）
2. 对比度修复（不动 `--c-line-strong`，避免全站从柔光变硬框）：**新增 `--c-control-border #8a8175`（对白 3.83:1）专供输入框与可交互控件描边**；`--c-neutral #716b62→#6b655c`（4.48→4.89）；`--c-ink-3` 在 3 种浅色底上的 4 处局部改用 `--c-ink-2`；立「`--c-brand` 禁作正文」守则（当前 0 处违规）
3. 图标单位纠错：所有 `:size` 按 rpx 重新标定（目标阶梯 24/32/40/48rpx 功能 + 96/144rpx 空态与结果页）
4. `base-button` md 档 80→88rpx；`brand`/`primary` 改名为 `ink`/`gold`（**仅改名，色值不动**；`primary` 现无任何调用）
5. **uview 主题桥对齐**：`uni.scss` 的 `theme("colors.*")` 改为直接映射 `--c-*`，消除 `var(--color-*)` 无定义导致的失效与回落

**验收标准**
- 预约页：必填为空时点提交，**同屏可见**指向该字段的错误（当前 0%）
- 预约页：`quote_hash` 为空时提交被拦截，拦截率 100%
- 订单详情：10 个动作全部可达，或已从契约移除并留记录
- 支付结果页：fail 态点重付前必有一次 `payStatus` 查询
- 对比度：正文全部 ≥4.5:1、控件边界 ≥3:1（用脚本复算，不靠肉眼）；输入框与 ghost 按钮描边实测 ≥3:1
- 图标：`:size` 只允许 24/32/40/48/96/144 六个值（**单位 rpx**，即目标 12/16/20/24/48/72px），其他取值出现次数 =0；tabbar 图标实测 ≥24px
- uview：全项目无未定义的 `var(--color-` 引用；`$u-type-primary` 实际渲染为品牌色而非继承色

**门禁**：P0-4 未拿到后端结论，阶段一不算完成，不得进入阶段二。

### 阶段二：反馈与组件（1.5 周 / 约 9 人天）

**目标**：让"点了有反应"，并把表单、空态从页面私有变成组件能力。

**范围**
- 组件：新增 `BaseInput` / `BaseField`，扩展 `base-empty`，改造 `price`
- 页面：`booking`（表单替换）、26 个调用 `base-empty` 的文件、`staff-list`、`app-tabbar`、`pages/order`

**产出**
1. 全站按下态：约 40 处 `@tap` 的 view 加 `hover-class`，统一用 `--c-surface-2` + 100ms
2. `base-empty` 增加 `errorKind`（网络错误可重试 / 业务受限不可重试 / 无权限），并接入 14 个 `empty-*` 图标做语境化
3. `BaseInput` + `BaseField` 落地，替换 `booking.vue` 内联表单；删除零引用死文件 `styles/form.scss`
4. `price` 收敛 4 档（sm 28/20、md 36/24、lg 48/30、xl 64/40），**调用处不再传裸字号**
5. `staff-list` 吸顶筛选条（日期 / 分类 / 排序）
6. tabbar 角标（数据源复用 `unread.total`）、订单 tab 图标修正
7. 列表滚动位置保留（`order.vue:220-234`）

**验收标准**
- 业务代码 `hover-class` ≥40 处（当前 2 个文件）
- 需要数据的约 30 页三态齐全，覆盖率 30/30
- 表单：错误提示贴字段下方，`@blur` 校验手机号，提交中全表单 disabled，失败保留输入
- 详情返回列表，滚动位置与 tab 选中 100% 保留；切排序后 scrollTop 归零
- `price` 调用处 `main-size`/`minor-size` 传值 = 0 处

### 阶段三：视觉系统收敛（1.5 周 / 约 7.5 人天）

**目标**：把"颜色表"升级成"有档位的系统"。本阶段全部是破坏性变更，必须单独批次、逐页截图回归。

**范围**
- `tokens.css`、`base-card`、全部 42 页的字号/圆角/间距/阴影
- 图标阶梯（17 种取值 → 6 个允许值）

**产出**
1. 字号 8→6 档：`fs-xs` 22→24rpx（影响 **124 处 / 约 30 页**）、`fs-xl` 36→38、`fs-2xl` 合并 44/52→48、`fs-display` 并入 `fs-2xl`、`fs-number` 仅由 `price` 消费
2. 圆角 6→5 档：删 `r-xl`（1 处死档）；立规 `pill` 只给按钮与标签、卡片固定 `r-md`、hero 固定 `r-lg`
3. 间距：补 `--sp-7 96rpx` 作页面级分区档；删 `sp-0-5`；高频私建值（160rpx 26 处、200rpx 10 处）归并
4. 卡片去 `shadow-card` 改纯描边；`shadow-float` 加深专供吸底与弹层
5. 图标阶梯 6 值：24/32/40/48rpx 功能 + 96/144rpx 空态与结果页
6. 动效 token：`dur-fast 150 / base 240 / slow 360` + `ease-out`；弹层统一 240ms

**验收标准**
- 字号 =6 档，`var(--fs-` 之外无裸 `font-size`
- 图标尺寸只允许 6 个值，其他取值出现次数 =0
- 圆角 ≤5 档、`r-xl` 引用 =0；间距 ≤8 档、`sp-0-5` 引用 =0
- 42 页逐页截图比对，间距误差 ≤2px、色值 ΔE ≤2、字号误差 =0
- 主包体积不因本轮增长（当前基线以 `npm run build:mp-weixin:check` 为准）

### 阶段四：多端与可访问性收口（1 周 / 约 4 人天，可与阶段三并行）

**目标**：把"只在某台手机上成立"的风险清掉。

**范围**
- 全局：`pages.json` 的 H5 配置、`booking.vue` fixed 底栏、关键控件的 `aria-label`
- 资产：9 个零引用 PNG、`tailwind.config.js`、`stores/theme.ts` + `utils/theme.ts`

**产出**
1. 真机验证三项并出结论：H5 导航冲突、键盘遮挡、sticky 与自定义导航栏冲突
2. 关键控件补 `aria-label`（图标按钮、纯图标 tab、图片）
3. 删除 9 个零引用 PNG（28.9KB）；`scaleToFill` 改为 `aspectFill`
4. 删除 tailwind 颜色层与运行时主题链路，`tokens.css` 顶部写明"颜色是设计资产，不接受运行时下发"

**验收标准**

## 五、关键决策（2026-11-05 已定稿）

| 编号 | 决策 | 结论 | 对计划的影响 |
|---|---|---|---|
| D1 | 订单详情 6 个动作 | **删契约** | P0-1 由「补 UI 3 人天」改为「收窄契约 + 清理孤儿 1.5 人天」 |
| D2 | 支付 fail 后重付 | **方案 A**：先查 `payStatus` 再决定能否重付 | P0-4 保留，但需后端先给幂等性与延迟 P95 |
| D3 | 字号 22→24rpx、按钮 80→88rpx | **接受** | 阶段三范围不变，124 处回归照做 |
| D4 | 主 CTA 是否改金底 | **可以**（按裁决维持黑底） | 阶段一仅做变体改名，不改色值 |
| D5 | 运行时主题死链路 | **删除** | 阶段四执行；`tailwind` 保留并重接（见 D5 说明） |

### D1｜订单详情 6 个动作：删契约（已定）

`apply_refund`、`confirm_complete`、`review`、`fill_questionnaire`、`upload_voucher`、`delete` 无 UI 出口，决定从契约移除。

**核实后的可达性**（决定"删"是清理还是功能损失）：

| 动作 | 其它入口 | 删除后果 |
|---|---|---|
| `review` 评价 | ✅ 我的 → 待处理 → 待评价（`user.vue:168`，仅 count>0 时可见） | 无损失，仅少一个入口 |
| `fill_questionnaire` 填问卷 | ✅ 消息路由（`useNotificationRouter.ts:36`）、我的、回访列表 | 无损失 |
| `apply_refund` 退款 | ❌ 全 App 零入口（`grep` 无命中） | **小程序不再提供自助退款** |
| `delete` 删单 | ❌ 零调用（`deleteOrder` 导入处为 0） | 小程序不支持删除订单 |
| `upload_voucher` 上传凭证 | ❌ 零调用（`uploadPayVoucher` 导入处为 0） | 线下收款凭证只能由后台/客服代传 |
| `confirm_complete` 确认完成 | ⚠️ `detail.vue:186` 有 import 但无调用 | 服务完成由后台或自动流转确认 |

**执行范围**：`shared/contracts/dto.ts:21` 的 `OrderActions` 从 11 项收到 5 项（`pay`/`cancel`/`change_date`/`pause`/`contact_advisor`）；删除 `api/order.ts` 中 `deleteOrder`、`uploadPayVoucher`、`applyRefund` 三个零引用函数；删除 `detail.vue:186` 未使用的 `confirmOrder` import；`detail.vue:201-213` 的 `actions` 初始值同步收窄。

**跨端影响**：`OrderActions` 仅 `newuniapp` 引用，`admin`/`pc` 零引用，无跨端影响。但服务端仍在计算这 6 个 flag（`dto.ts` 注释「由服务端计算」），需同步确认是否停止下发——**不影响功能，只是冗余字段**。

**待你确认的后果**：上表 4 个 ❌ 项意味着小程序放弃自助退款、删单、上传凭证、确认完成。若其中任一项业务上需要用户自助完成（尤其退款），D1 应改为「补 UI」而非「删契约」。

### D2｜支付 fail 之后：方案 A（已定）
先查 `payStatus`，确认未支付才允许重付。**前置依赖**：后端提供 `payStatus` 幂等性与回调延迟 P95；若拿不到数据，退化为方案 B（只给「稍后查询」与「联系客服」），**不得凭 32 秒轮询超时判定失败**。

### D3｜两项全局规范变更：均接受（已定）
- 字号 `fs-xs` 22→24rpx：影响 124 处 / 约 30 页
- 主按钮 80→88rpx（40→44px 触控标准）：影响 20+ 页按钮高度
**执行要求**：两项均属破坏性视觉变更，必须单独批次 + 42 页截图比对，不与 P0 混做。

### D4｜主 CTA：维持黑底（已定）
视觉侧建议改金底（深墨字 7.43:1 达标），交互侧认可，但有三条约束：一屏只允许一个金底按钮、3 处列表内按钮须同步改黑、需加 1rpx 深描边。
**现状**：全站**没有金底按钮**——`variant="primary"`（金底）调用 0 处，33 处主按钮全部是近黑（`--c-ink`，18.05:1，已达标）。
**结论：本周期不改，维持黑底。** 理由是金底对米白页面的**边界对比度仅 2.25:1**（低于控件可辨识的 3:1），要补救就得加描边；且 30+ 处主按钮一次变金是视觉语言反转，需 42 页全量回归，而 P0 闭环还没修完。阶段一只做变体改名（`brand`→`ink`、`primary`→`gold`），色值不动。
**门禁条件**：若后续要做，需同时满足——① `--c-brand` 加深到对米白 ≥3:1，或固定 1rpx 描边；② 一屏一个规则写进设计评审；③ 3 处列表内按钮改黑。满足后再单独排期。

### D5｜运行时主题链路：删除（已定）
- `stores/theme.ts` + `utils/theme.ts` 的运行时主题生成（`vars` 被写 3 次、读 0 次）——**删除**，约 0.5 人天。它现在不产生效果，但会诱导下一个人"修好"它，那一刻整站配色就被后台配置覆盖。
- **`tailwind.config.js` 不能删**：它是 `uni.scss` 里 30+ 个 `$u-*` 变量的取值来源，38 个 uview 组件依赖它。正确处理是**重接**（阶段一第 5 项），且必须在本链路删除之前完成，否则 uview 会失去唯一的 `--color-primary` 来源。

### D6｜人力与节奏：不后置（已定）
上表按 1 名前端估算，总计约 **31 人天 / 6 周**（前端侧自下而上估 26 人天、区间 23–30，不含阶段四的真机验证，与本表交叉校验一致）。按 D6 决策，四阶段按序执行，阶段三不后置。
