# 基于 niucloud 的婚庆服务平台从零开发文档

文档版本：1.0。编写日期：2026年9月13日。

文档性质：新项目的产品需求、开发约束、实施路线与验收基线。本文描述待开发目标，不表示功能已经实现或通过微信真实环境验收。

使用方式：将本文件复制到新项目的 `docs` 目录，即可作为开发总纲。本文不依赖旧项目代码、数据库或其他旧文档。新项目以 niucloud 官方代码为基础独立建设，旧系统不继续重构。

## 一、项目目标与已确定范围

建设一套婚庆服务预约与经营管理平台，打通“咨询选人 → 报价预约 → 人员确认 → 首笔到账锁档 → 婚前准备 → 履约 → 尾款 → 售后与结算”。

### 1.1 产品入口

| 入口 | 职责 | 边界 |
| --- | --- | --- |
| 微信小程序客户入口 | 查看人员及案例、预约、付款、订单、问卷、变更、售后、评价、活动报名。 | 客户业务唯一交易入口。 |
| 同一小程序的服务人员工作台 | 接单、档期、手工档期、履约、资料、团队、结算、海报。 | 经审核取得人员身份后开放，不能由客户自行切换获得权限。 |
| niucloud 站点管理后台 | 顾问跟进、人员团队、服务报价、订单档期、问卷售后、收退款结算、内容及运营。 | 复用框架后台与权限体系。 |
| 电脑展示网站 | 品牌、人员介绍、案例、资讯、联系方式及小程序引导。 | 无客户登录、个人中心、预约和付款。 |
| 微信服务号 | 关注绑定、业务通知、小程序跳转。 | 不建立另一套交易端；关注与绑定是接收通知的必要条件。 |

### 1.2 开发基线

- 基于用户指定的 **niucloud PHP SaaS 框架**，不是 Java 版本、商城系统改造或其他同名产品。
- 建设一个独立的婚庆应用，使用框架的插件机制承载，暂定标识为 `wedding_service`，显示名称为“婚庆服务”。创建时类型选择“应用”；最终字段取值以固定版本的生成器为准。
- 首次上线运营一个站点，保留 niucloud 的站点隔离能力；不额外建设招商入驻、站点售卖、租户计费或跨站点人员市场。
- 预约单位为人员的自然日，默认业务时区为 `Asia/Shanghai`，同一人员同一天只能有一份有效占用。
- 支付仅微信小程序支付与受控线下收款。人员结算直接关联业务应付与付款记录，不经过会员钱包。
- 所有站外业务通知统一使用微信服务号。站内消息与待办保留；短信仅用于验证码。
- 不迁移旧代码、旧表、旧接口和旧配置。历史数据导入属于独立后续项目，不属于首版。
- 新系统启用日期前的未履约、未退款、未结算责任另建交接清单；不能因放弃旧系统而取消真实业务责任，也不能在两套系统重复收款。

### 1.3 明确不开发

企业微信及其应用消息、机器人、通讯录绑定等功能全部排除；不建立其他站外业务通知渠道，也不使用小程序订阅消息替代服务号推送。

不开发钱包、充值、余额支付、会员提现、支付宝、组合支付、购物车、优惠券、方案分享、独立套餐预约、分场次预约、自助换人、晒单奖励、旧成本报表、客户确认函推送、PC 账号体系和独立 H5 业务端。

不因框架自带以上模块而开放入口。通过应用菜单、渠道配置及服务端业务校验收缩范围，不删除框架公共核心文件。订单服务约定、真实付款退款记录、工作人员人工协调换人仍然保留。

### 3.1 插件组织

官方插件生成目录为 `niucloud/addon/插件标识`。标识须符合当前生成器要求，包含下划线；不要使用不符合要求的 `wedding` 单词标识。

建议组织如下，最终以固定版本实际生成结果为准：

```text
niucloud/addon/wedding_service/
  app/
    adminapi/          后台业务入口与路由
    api/               小程序业务入口与路由
    service/core/      订单、档期、资金等共用业务规则
    service/admin/     后台操作编排
    service/api/       小程序操作编排
    model/             业务数据模型
    validate/          参数与业务输入校验
    dict/              状态、菜单、通知、任务等字典
    listener/          框架事件适配
    job/               异步业务任务
    lang/              中文提示与语言资源
    upgrade/           版本升级处理
    event.php          事件登记
  admin/               插件管理端源文件
  uni-app/             插件小程序源文件
  web/                 可选电脑展示页面
  package/             页面及打包配置
  resource/            插件资源
  sql/                 安装与升级所需数据定义
  Addon.php            插件生命周期入口
  info.json            插件信息
```

目录用于界定职责，不要求提前创建所有空目录。安装后框架会向管理端、uni-app、web 工作目录生成对应代码。阶段 M0 必须验证“开发文件 → 打包归集 → 全新安装”的流向，确定各端唯一维护源，避免源文件与安装副本双向手工修改或重装覆盖开发成果。

控制器只处理认证、输入和结果；核心规则集中在业务服务。同一项付款确认、锁档或退款规则供后台、小程序、回调和任务共同调用，不能分别实现。

## 四、角色与数据权限

| 角色 | 可执行事项 | 数据范围 |
| --- | --- | --- |
| 游客 | 浏览品牌、公开人员、案例与可约概况。 | 不展示客户资料、具体档期联系人或内部价格。 |
| 客户 | 本人预约、付款、问卷、申请、售后与评价。 | 本人订单及被明确授权的信息。 |
| 服务人员 | 接单、本人档期、手工档期、履约、个人结算与资料。 | 本人参与订单的必要服务信息，不默认显示他人收入。 |
| 队长 | 授权团队人员、待办、档期及分成查看。 | 当前有效团队授权，不能跨团队读取数据。 |
| 顾问 | 客户分配、跟进、报价协助及相关订单。 | 分配给本人或明确授权的客户。 |
| 运营 | 人员审核、报价、订单确认、变更、内容、售后。 | 当前站点授权范围，不默认拥有出款权限。 |
| 财务 | 线下收款审核、退款审核、结算和对账。 | 当前站点资金业务；出款与制单按权限分离。 |
| 站点管理员 | 本站点配置、授权及异常协调。 | 不读取其他站点业务。 |
| 平台管理员 | 框架运维与站点管理。 | 不因平台身份默认获得所有婚庆资金操作权。 |

一个会员可兼具客户和服务人员身份，但身份切换只影响界面，服务端逐次鉴权。后台用户与会员是不同账号域，通过有记录的关联关系连接。

所有业务记录、查询、导出、附件访问、缓存键、队列任务和通知都携带站点范围。站点身份来自可信认证上下文；回调通过已保存交易定位站点并校验，不能信任请求随意提交的 `site_id`。客户端传入订单编号不代表拥有该订单。

首版隔离边界为站点；同一真人在两个站点建立独立人员档案时不共享档期。上线只运营一个站点，多站点人员互通需要另行设计，不暗中跨站读取。

## 六、主流程与订单规则

### 6.1 预约顺序

1. 客户选择服务地区和日期，再选主服务人员、专属套餐、附加项和协作人员。
2. 服务端重新计算报价、校验人员上下架与档期，生成有期限的报价快照。
3. 客户确认服务内容、取消退款约定、付款安排后提交订单；此时不代表已锁档。
4. 所有参与人员分别确认，管理员确认整单后开放首笔付款。任一人员拒绝则回到人工协调，不能跳过其确认收款。
5. 首笔实际到账后，对全部参与人员同一天的档期统一锁定。全部锁定成功，订单进入待服务；发生冲突则进入异常处理并安排退款，不能只锁住部分人员。
6. 婚前确认地点、联系方式与准备事项；人员按权限开始和完成服务，管理员确认整单履约完成。
7. 全款订单进入结算检查；分期订单继续收尾款，款项结清、售后满足条件后进入结算。

默认不为客户创建订单自动预占档期，付款页明确提示“到账后以锁档结果确认，异常将处理退款”。管理员可建立限时预留；预留必须有负责人、原因、失效时间和可关联订单，同一订单到账时转换占用，不能与自己的预留冲突。若后续改为付款前短暂占档，必须单独变更规则与并发验收。

### 6.2 报价规则

- 套餐必须归属于可提供该服务的人员；地区费用、附加项和协作人员费用逐项展示。
- 金额由服务端生成。前端只提交选择项，不能提交可信的总价或抽成结果。
- 报价保存套餐名称、内容、地区、价格、人员、费用承担与分配规则的版本快照，历史订单不读取当前商品价格重算。
- 金额内部按人民币“分”保存和计算，百分比使用精确比例；框架如使用元字符串，适配时做精确转换，禁止浮点误差。
- 定金比例是站点开工必填配置，必须大于零且不超过总额；页面明确显示具体定金和尾款金额，不提供隐含比例。
- “定金”与“订金”等服务约定由运营提供经确认的文案，系统不得凭名称自动推导没收、双倍返还等规则。
- 后台调整价格须有原因与权限；收款后不得直接覆盖总价，必须通过客户确认的变更单。

### 6.3 多维状态

不要把支付、履约、退款、结算挤在一个订单状态字段中。

| 维度 | 建议状态 | 转换要求 |
| --- | --- | --- |
| 订单主流程 | 待人员确认、待管理员确认、待首笔付款、待服务、服务中、服务完成、已取消、异常待处理。 | 操作校验前置条件并记录日志，已取消订单不因迟到付款恢复。 |
| 人员确认 | 待确认、已接受、已拒绝、已撤销。 | 全员接受后管理员才能整单确认；变更人员或日期重新确认。 |
| 收款汇总 | 未收款、部分收款、已收齐、存在异常款。 | 从确认收款与应收分配计算；退款独立展示。 |
| 付款流水 | 待支付、处理中、成功、已关闭、失败。 | 成功以可信回调或查单为准，不相信前端支付结果。 |
| 履约明细 | 未开始、服务中、已完成、异常。 | 逐人记录；整单完成须全部完成或有批准的替代处理。 |
| 暂停控制 | 正常、暂停中。 | 独立于主流程，保存暂停前状态及恢复条件。 |
| 退款 | 待审核、已驳回、待执行、处理中、成功、失败待处理、已撤销。 | 申请、批准、渠道到账分开，失败不直接当成功。 |
| 结算 | 待生成、待核对、待审批、待付款、付款中、已结清、冻结。 | 退款与付款占用互斥，实际到账才核销。 |

“服务完成／尾款待收”是合法组合，不是应自动取消的订单。退款成功不必然代表整单取消，部分减项退款仍可继续履约。业务关闭条件为履约或取消已有结论、收退款已对平、售后已处理、人员结算或补交已结清。

### 6.4 档期与并发

- 平台订单、有效手工档期、内部预留共同参与占用检查；公开页面只显示忙闲，不泄露私单资料。
- 最终占用必须有数据库级唯一性或等效原子保护，不能仅靠先查询后保存，也不能仅用缓存锁。
- 多人员按固定顺序处理，在同一事务中全部取得档期或全部失败。
- 支付成功事实先持久保存；锁档失败不得回滚或丢弃真实收款事实，应产生一条唯一补偿任务。
- 手工档期编辑与取消同样做权限和冲突检查；已被平台订单使用的占用不能直接被手工覆盖。
- 取消、改期、预留到期释放时验证占用的当前归属，旧任务不得释放已分配给新订单的档期。

### 6.5 改期、加项、暂停与人工换人

| 操作 | 默认规则 |
| --- | --- |
| 改期 | 申请包含新旧日期、人员、费用差；全员及客户确认后，原子取得新档期并释放旧档期。失败则保留原安排。 |
| 改期加价 | 经确认后形成变更待收款，到账后执行最终换档；执行失败保留原订单并退还异常变更款。 |
| 改期降价 | 换档成功后按批准差额申请原流水退款，退款失败不静默改回档期。 |
| 加项 | 保存新增内容与价格快照；涉及新人员必须确认并锁档，不能仅增加订单金额。 |
| 暂停 | 默认保留现有占档，停止新的履约、客户付款入口及结算发起；退款、查单和售后处理继续。记录原因、负责人和期限。 |
| 暂停到期 | 创建人工处理待办，不自动取消、不自动退款、不静默恢复。恢复时检查日期、人员、资金和待处理变更。 |
| 暂停期间迟到付款 | 保留到账事实并进入人工核查，不触发履约推进；若已取消按迟到付款规则处理。 |
| 人工换人 | 仅在无法履约等情形由运营发起，客户与新人员确认，校验新档期并保留原人员责任记录。无客户自助换人入口。 |

同一订单默认只允许一笔影响日期、人员或金额的变更处于执行中。变更款与原订单应收分别归属；变更失败退款不得冲掉原订单合法应收。

## 七、收款、退款与结算

### 7.1 金额口径

| 指标 | 定义 |
| --- | --- |
| 有效应收 | 原成交金额加已生效加价，减已生效减价或取消减免；未生效变更不覆盖原值。 |
| 累计确认收款 | 微信确认成功款与审核确认的线下款，退款不删除原收款。 |
| 成功退款 | 已确认退款成功的金额；处理中金额单列。 |
| 净收款 | 累计确认收款减成功退款。 |
| 待收金额 | 按有效应收及对应正常收款分配计算，最低为零；异常迟到款、待退多收款不得抵充其他应收。 |
| 待退金额 | 已批准且尚未成功退回的金额，与异常多收款明确关联。 |
| 可退额度 | 单笔原流水实收减成功退款减其他有效退款占用，不能跨流水或跨订单借用。 |

减项退款必须同时有应收减免依据；否则退款后会形成需解释的应收缺口。所有汇总能追溯到收款、应收调整、退款和分配明细。

示例：原订单10000元，定金3000元、尾款7000元。批准减项2000元后，有效应收8000元；若只收定金，尾款为5000元；若已收齐，则退2000元后净收款8000元，待收为零。取消后迟到的3000元单列异常待退，不算新订单营收。

### 7.2 付款控制

- 支付请求绑定站点、订单、应收期次、金额、付款渠道及有效期；同一期次重复点击复用有效支付请求或明确关闭旧单后重建。
- 首笔付款设超时规则；尾款进入逾期提醒，不复用首笔超时取消逻辑。
- 微信回调与主动查单共用一次性结果处理，验证交易归属、金额、币种和渠道记录。
- 取消时关闭仍有效的支付请求；关单结果未知继续查单。已经取消后查到支付成功，保留取消状态并进入补偿退款。
- 已发起支付流水未确认关闭、线下凭证待审时，不允许直接切换当前期次渠道。设置变更只影响后续新请求。
- 所有外部调用都允许“结果未知”，不能因为请求超时直接新建一笔付款、退款或转账。

### 7.3 受控线下收款

记录付款人、实际收款主体、金额、日期、用途、凭证、登记人和审核人。客户上传凭证只表示待审，不增加实收、不锁档。审核确认后进入与线上相同的到账业务处理。

实际收款方区分公司与具体人员。凭证驳回可重交，旧版本保留。登记与审核默认分离；特殊单人处理需权限、原因和审计。人员代收是结算抵扣依据，不能同时计入平台现金到账。

### 7.4 退款控制

退款申请必须有原因、关联服务内容和应收调整依据；审核人确认金额、原流水分摊及服务是否继续。客户不能指定任意退款收款账户。

一笔退款业务可拆为多笔原流水退款，每条记录独立跟踪。提交前原子占用额度；重复提交复用同一业务记录。退款失败需先确认渠道终态再释放额度，结果未知继续查询，禁止立即重发不同退款号。

线上原路退回；线下记录实际退回主体、对象、凭证及财务复核，不能伪造微信退款成功。混合历史收款按原流水分别退款，不把线下款退成微信款。

已结算或转账中的订单申请退款，先冻结后续结算并转人工处理；记录资金来源、人员追回应收或平台承担依据。实际已到账结算保留原记录，通过调整单处理，不直接反写为未付款。用户退款进度与人员追偿进度分别展示。

### 7.5 分配与结算

V1 采用按订单、按人员明细结算；周期结算只汇集尚未结算的明细，不重复计算已结算订单。包月与多层分成留到 V2。

- 每笔服务收入划分到具体人员或明确的公司自营项目，形成分配基数快照。
- 每个人员明细保存公司抽成、队长抽成、人员应得及费用承担规则；同一基数上明确计算，避免顺序不同导致双扣。
- 默认人员应得为分配基数减公司抽成减队长抽成；队长抽成默认零，实际比例和固定额开工配置，无有效规则不能生成结算。
- 多人员金额分配总和等于订单可分配净额；一分钱的舍入余差分配到确定的最后一条明细并可追溯。
- 代收抵扣应归属实际收款人员：平台应付为人员应得减其持有的订单代收净额；结果为负数时生成平台抽成等应补交，不能生成负数转账。
- 退款、费用与调整先分摊到责任明细，再计算结算；费用项必须有规则和凭证，不能无依据从人员所得扣除。
- 队长分成另建应付明细；队长同时提供服务时，两种所得分别展示。
- 首版默认履约完成、客户款已收齐、无未决退款或售后、结算冷静期已满足后才能审批。冷静期为站点必填设置，可以明确配置为零。
- 退款申请与结算占用必须互斥；结算通过后再次出款前复核，没有权限的运营不能绕过审核。
- 转账区分已受理、待领取、处理中、实际到账、失败、退回等渠道事实；映射到业务状态后显示中文含义，只有真实到账才结清。
- 未开通适用商家转账时可采用审批后的线下出款并上传凭证复核，不能把“点击发放”当到账；微信转账路径验收通过前保持关闭。

示例：订单可分配净额10000元，公司20%、队长5%，人员应得7500元。公司收到客户全部款项时，应付人员7500元、队长500元；人员代收全部10000元时，该人员应补交2500元，平台仍需向队长支付500元。平台现金、分成收入和代收款分开统计。

## 八、微信服务号关注绑定与推送

### 8.1 三个独立状态

| 状态 | 含义 |
| --- | --- |
| 关注状态 | 指定服务号下该微信用户是否仍关注，以可信事件及必要的状态核对为依据。 |
| 绑定状态 | 该服务号微信身份是否经本人确认关联本站点会员。 |
| 可接收状态 | 已关注、有效绑定、账号和业务权限有效、实际模板及配置可用。 |

未绑定仍可浏览、下单、查询和售后；站外推送必须关注并绑定。客户在下单和“我的”中看到明确接收提示，工作人员工作台持续显示未完成提醒，不把通知故障变成无法办理退款的障碍。

### 8.2 本人双确认流程

1. 已登录小程序的会员发起绑定，服务端生成限时、限次、一次性绑定码，绑定站点、会员及本次请求。
2. 小程序展示服务号名称、关注方式、验证码和操作说明；不把完整身份信息编码进公开二维码。
3. 用户关注服务号后提交绑定码，服务端从可信微信事件取得该服务号下的 OpenID，形成待确认关联。
4. 用户回到原会员的小程序确认，展示可核对的脱敏微信信息和服务号名称；确认成功才写入有效绑定。
5. 展示关注、绑定及可接收状态，允许本人显式解绑和重新发起。

建议初始参数：绑定码有效期5分钟，单次请求最多校验5次，重新发起后旧码失效；同时限制微信身份、会员和来源请求频率。记录码的不可逆校验值，避免日志泄露可用绑定码。

同一站点、同一服务号下，一个微信身份只绑定一个会员，一个会员只保留一个有效接收身份；跨账号冲突不覆盖原关系，先走原账号解绑或经核实的申诉流程。不同 AppID 下的 OpenID 不能当成同一个值，UnionID 不能作为无条件存在的自动关联依据。

取消关注只停止推送，保留绑定；重新关注后核对绑定及权限恢复接收。主动解绑立即停用原接收关系并使旧待确认请求失效。注销按框架账号流程停用通知，必要订单记录按保留策略处理。

### 8.3 工作人员身份关联

后台登录人员发起关联请求 → 已登录会员在小程序确认 → 后台再次确认或由有权限管理员审核 → 建立站点内后台用户与会员关系。必须保存双方身份、发起与确认时间、审核人和撤销记录。

手机号或姓名相同只可用于提示，不能自动取得工作人员权限。后台账号停用、离职、团队变化、解除关联后立即重新计算接收对象；绑定服务号本身不赋予后台权限。

### 8.4 通知矩阵

| 事件 | 接收人 | 跳转目标 |
| --- | --- | --- |
| 新订单待确认 | 本单相关人员、负责运营。 | 人员确认页或授权订单详情。 |
| 可付款、首笔到账及锁档结果 | 客户；相关人员只收职责所需结果。 | 订单详情。 |
| 婚前待办、问卷待填 | 客户及负责人员。 | 待办或指定问卷。 |
| 服务日期或人员变更结果 | 客户及当前相关人员。 | 变更详情。 |
| 暂停与恢复 | 客户、相关人员及负责人。 | 订单进度。 |
| 尾款到期、逾期 | 客户、负责顾问或运营。 | 付款或应收待办。 |
| 退款受理、结果与异常 | 客户、相应财务负责人。 | 退款详情。 |
| 售后分配、处理结果 | 客户及当前处理人。 | 工单详情。 |
| 结算、到账、补交 | 对应人员、队长及财务。 | 本人结算或补交详情。 |
| 候补、活动结果 | 对应申请人和责任人。 | 候补或报名详情。 |

通知只含最少必要摘要，客户看不到分成，人员看不到无权查看的他人收入。后台工作人员由服务号跳入小程序的授权待办页；复杂财务审批提示前往后台处理，不暴露后台登录凭证。

### 8.5 模板与可靠性

- M0 在实际服务号后台核对认证、行业类目、模板权限、小程序关联与跳转能力，为每个业务事件记录真实模板映射。
- 不能假设框架自带模板适用于婚庆，也不能承诺已关注就能无限推送。无适配模板的事件保留站内消息和人工待办，明确列为未具备站外推送能力。
- 业务提交成功后可靠产生通知任务；任务入队失败可从持久记录补发，不能导致资金业务回滚。
- 去重键包含站点、业务事件、对象、接收人和版本；重复回调不产生重复消息。
- 发送前复核关注、绑定、权限及业务状态；已付款不发待付款，已改期不发旧日期提醒。
- 区分待发送、渠道受理、失败、跳过；渠道受理不等于用户已读。
- 可重试错误按退避策略有限重试；无关注、无权限、模板缺失等进入明确原因，不无限重试。
- 消息跳转后重新登录鉴权，旧通知不能绕过订单当前权限。微信不可用时站内业务仍能运转。

## 十、业务数据设计基线

以下为拟定业务实体，名称不表示 niucloud 已有同名表。物理表采用配置表前缀加 `wedding_service_` 业务前缀，框架会员、后台用户、站点与支付表仅关联，不复制。

### 10.1 通用约定

- 业务实体保存主键、站点、创建与更新时间、必要操作者；主流程记录版本号用于并发校验。
- 金额整数分；服务日期单独存储自然日，时间戳统一存储标准，展示按业务时区转换。
- 交易、审批、答案、结算等正式事实保留历史，撤销用状态或调整单，不物理删除。
- 不将所有结构塞进一个扩展字段。仅价格、服务约定、模板等不可变快照可用结构化快照存储。
- 关联的每一级对象都校验同站点；唯一约束包含实际业务作用域。

### 10.2 实体清单

| 领域 | 建议实体 | 核心字段与关系 |
| --- | --- | --- |
| 人员 | `staff`、`team`、`team_member` | 会员关联、审核状态、服务类型、地区、公开资料、团队有效期。 |
| 身份 | `staff_user_link`、`identity_request` | 后台用户、会员、站点、双确认状态、有效期与撤销记录。 |
| 展示 | `staff_work`、`staff_certificate`、`favorite` | 人员或内容关联、素材引用、审核状态；同人同对象收藏唯一。 |
| 报价 | `package`、`price_rule`、`addon_item`、`quote` | 套餐所属人员、地区费用、版本、有效期、价格和服务快照。 |
| 档期 | `schedule_occupancy`、`manual_schedule`、`schedule_reservation` | 人员、自然日、来源、归属对象、有效期限；有效占用唯一。 |
| 订单 | `order`、`order_item`、`order_staff`、`order_log` | 客户、日期地点、状态、报价快照、人员确认、版本、操作历史。 |
| 变更 | `order_change`、`order_change_item` | 变更类型、前后快照、差额、确认结果、执行状态。 |
| 应收 | `receivable`、`receivable_adjustment` | 订单与变更来源、定金／尾款／加项用途、应收额、到期日、减免依据。 |
| 收款映射 | `payment_allocation`、`offline_receipt` | 框架支付编号、应收分配、收款方、凭证、审核、异常款标志。 |
| 退款 | `refund_request`、`refund_item` | 申请、审批、原流水、占用金额、框架退款编号、结果。 |
| 结算 | `settlement`、`settlement_item`、`settlement_adjustment` | 人员、订单、分配快照、代收抵扣、审批、冻结原因。 |
| 出款补交 | `settlement_payment`、`collection_due` | 框架转账编号或线下凭证、应付分配、补交应收、到账核销。 |
| 服务号 | `wechat_binding_request`、`wechat_binding` | 服务号 AppID、OpenID、会员、确认记录、有效绑定；关注事实优先复用框架。 |
| 消息任务 | `business_event`、`business_todo` | 事件唯一键、目标、状态版本、通知映射、负责人、截止时间。 |
| 客户跟进 | `customer_profile`、`lead`、`followup` | 联系人、会员可选关联、顾问、婚期、来源、计划、成交订单。 |
| 问卷 | `questionnaire_version`、`questionnaire_assignment`、`answer_draft`、`answer_submission`、`answer_supplement` | 发布快照、订单与人员、草稿版本、正式答案及补充历史。 |
| 售后评价 | `service_ticket`、`ticket_log`、`review`、`review_reply` | 订单、分类、责任人、处理时限、退款关联、评价审核。 |
| 海报月报 | `poster_record`、`monthly_report` | 模板与统计版本、生成结果、展示调整，附件访问权限。 |
| 候补 | `waitlist` | 客户、人员、日期、通知期限、状态、转成订单关联。 |
| 活动 | `activity`、`ticket_type`、`registration` | 时间、票价、库存、报名、付款退款关系。 |

正式表设计按阶段补充类型、索引、约束和字段说明，不要求一次性建齐未来模块。对于框架已有可靠消息持久化、导出或粉丝状态能力，直接映射复用，避免同一事实维护两份互相冲突的表。

### 10.3 必须保证的唯一性

- 同站点人员自然日有效占用唯一；历史释放记录不妨碍再次预约。
- 同站点会员与后台用户的有效关联符合一对一约束；同站点服务号有效绑定符合第八章规则。
- 框架支付、退款、转账结果的业务处理编号唯一。
- 同订单同应收的支付分配不能重复入账；退款拆分总额不能超过批准额。
- 同一订单人员的有效结算分配不重复；周期结算不能再次选中已占用明细。
- 同一事件和接收人的通知去重；绑定码只能被成功消费一次。

## 十一、业务操作契约与框架事件

下面列出待实现的业务操作名称，不是可直接调用的官方 API 地址。M0 根据真实框架路由规范确定路径，在新项目维护 `docs/接口契约.md`；每项记录权限、输入、结果、错误、幂等及状态前置条件。

| 操作 | 关键输入 | 服务端保证 |
| --- | --- | --- |
| 查询可约与生成报价 | 地区、日期、人员、套餐及附加项。 | 当前可约仅供参考，报价有版本与有效期。 |
| 创建订单 | 有效报价、客户确认、请求唯一标识。 | 重新校验；重复请求返回同一订单。 |
| 人员／管理员确认 | 订单、版本、接受或拒绝、原因。 | 当前角色有权且状态允许；不能重复推进。 |
| 创建付款请求 | 订单、应收期次、渠道、唯一标识。 | 服务端定金额；锁定有效渠道与请求关系。 |
| 审核线下款 | 凭证记录、版本、结论。 | 分权审核、一次入账、复用锁档逻辑。 |
| 开始／完成服务 | 订单及人员明细、版本。 | 当前参与人员可操作，暂停或取消不推进。 |
| 提交／处理变更 | 类型、目标安排、报价、确认记录。 | 先取得一致确认，执行时再校验档期及资金。 |
| 申请／执行退款 | 原订单、原因、金额、审批结果。 | 原流水分摊与额度保护、权限和结算互斥。 |
| 生成／审批／支付结算 | 明细范围、规则快照、版本、审批。 | 不重复选单；出款状态不明时查询原单。 |
| 创建／确认绑定 | 当前会员、绑定请求、确认动作。 | 微信身份来自可信事件，双确认且一次生效。 |

所有写入返回稳定业务编号、中文可理解结果及最新状态。错误至少区分无权限、状态已变化、报价失效、档期冲突、金额不符、渠道处理中、退款额度不足、结算冻结和绑定冲突；状态冲突提示刷新，不诱导重复付款。

官方已确认的扩展事件包括 `PayCreate`、`PaySuccess`、`RefundSuccess`、`TransferSuccess`、`NoticeData`。婚庆监听器先验证本业务标识和站点，不处理其他插件订单。事件参数、触发时机、是否在事务内以及返回值必须读固定版本源码核实；不假设事件天然保证业务恰好执行一次。

公众号关注、取消关注和用户消息的扩展入口须在 M0 核实实际版本，本文不虚构事件名称。支付等适配层负责将框架事实转换为本项目业务结果，不重新实现微信签名协议。

## 十三、安装、配置、数据与上线维护

### 13.1 初始配置

必须设置品牌与客服、服务地区、人员类型、有效套餐、定金比例、报价有效期、首笔付款期限、内部预留期限、提醒计划、结算规则、冷静期、退款服务约定、角色权限、微信账号与商户参数。

微信密钥、证书及存储凭据使用框架安全配置方式，按测试和生产环境隔离，不放入插件源文件、文档、演示数据或可公开附件。模板编号、AppID、商户号和域名使用实际配置，文档不填虚构的可用值。

### 13.2 安装与升级

- 插件安装只创建自身业务表、菜单、字典和必要基础配置；不植入生产管理员密码或演示财务流水。
- 重复安装初始化、重复站点初始化不得重复生成菜单、角色或业务配置。
- 每次升级有版本号、变更内容、数据兼容说明、备份和失败恢复方法；正式交易数据不得因升级丢失。
- 在全新框架安装和上一插件版本升级两条路径分别验收。
- 停用插件先停止新业务，但提供未结事项处理与历史查询安排；存在真实订单资金记录时禁止普通卸载直接删表。
- 删除测试数据或正式卸载须先区分环境、完成导出和核对。生产数据清理是独立管理动作，不放进默认卸载脚本。

### 13.3 生产准备

测试与生产隔离数据库、Redis、存储、微信配置和回调地址；部署验证 HTTPS、域名、小程序合法域名、时间同步、队列常驻、计划任务及备份恢复。

建立数据库与附件备份、恢复演练、任务失败与积压告警、支付异常和退款结算对账。日志与导出设置访问范围及保留期限。表单收集以服务必需信息为限，客户隐私不进入公开海报与页面。

回退应用代码不能倒退微信已发生的收付款事实。版本失败时暂停新增资金动作，保留回调、查单和核对通道，通过修复或兼容版本处理，不能直接恢复旧数据库覆盖新交易。
