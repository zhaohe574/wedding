# 重构功能优化方案

更新日期：2026年9月13日。

## 一、方案定位

项目定位为婚庆服务预约与经营管理平台，围绕“咨询选人 → 报价预约 → 收款确认档期 → 婚前准备 → 服务履约 → 尾款 → 售后与结算”组织功能。

本版依据当前工作区的现行功能、业务规则、变更记录与相关页面重新整理，取代此前基于旧版本形成的去留建议。本文只说明业务功能，不包含编码方案。当前工作区已有大量调整，不代表全部已经上线；真实付款、退款、转账、服务号推送和小程序保存图片仍需实机验证。

全文区分三种结论：

- **现行保留**：当前已有业务，重构继续承接。
- **建议优化**：需要完善或简化的目标行为，不代表当前已经具备。
- **已退役／按需启用**：已退出的能力不再复建；仍在使用但非主线的功能按实际业务安排投入。

## 四、首批重点优化

### 1. 订单成为统一业务入口

订单详情固定显示服务安排、负责人员、付款明细、婚前准备、处理记录和当前待办。问卷、变更、售后、评价通过订单进入，同时保留工作人员需要的跨订单列表。

履约与付款分开表达，例如“服务中／已付定金”“服务已完成／尾款待付”。每个状态都说明下一步由谁做、什么时候做。

多人员订单显示每位人员的确认与服务情况，明确对客协调负责人；人员只能查看授权范围内的客户信息与金额。

### 2. 明确档期何时真正得到保障

当前业务规则以首笔实际到账后的锁档为关键节点。重构必须清楚告知客户付款前是否已有临时保障、保障期限及过期影响，不把提交订单展示成已确认占档。

付款后如遇冲突或迟到付款，展示异常处理与退款进度，不恢复已经取消的订单，也不让客户误以为付款后可以继续履约。

平台订单、手工档期与内部预留统一参与冲突判断。手工档期保留来源、日期、联系人及履约记录，其收入不能自动混入平台营业额。

### 3. 收款、尾款、退款与结算分别说清楚

- 订单金额区分应付总额、已付、待付和已退，每笔收款说明用途。
- 定金和尾款分别展示付款条件与期限；完成服务后仍有欠款，继续跟踪应收。
- 线下收款标明实际收款方、金额、凭证和审核人，上传凭证不等于到账。
- 退款按原付款记录处理，部分退款、失败退款和异常付款均有明确状态。
- 已结算或转账中需要退款时，保留资金保护，并进入人工处理待办，记录责任人及批准的资金处理方式。
- 结算展示公司、队长与人员的分配依据，区分已发起转账、待领取和实际到账。
- 平台抽成补交单独说明应补金额、已补金额和所属订单，不能与客户尾款混淆。

### 4. 服务号推送形成完整接收流程

客户接收路径：登录小程序 → 获取绑定入口 → 关注服务号 → 提交绑定信息 → 返回小程序确认 → 查看接收状态。

工作人员在此基础上完成本人后台账号与平台账号的关联，经确认后接收职责范围内的业务提醒。不能仅凭手机号或姓名关联工作人员身份。

| 情况 | 应有行为 |
| --- | --- |
| 已关注、已绑定 | 满足其他发送条件时推送相关业务通知。 |
| 已关注、未绑定 | 提示完成平台账号绑定，不能认定可接收业务通知。 |
| 已绑定、未关注 | 提示关注；账号绑定关系仍保留。 |
| 取消关注 | 停止推送，不自动解绑平台账号。 |
| 主动解绑 | 停止向原微信身份推送；重新接收需重新绑定确认。 |
| 绑定码过期或冲突 | 给出原因及重新发起、核实身份的入口。 |
| 发送失败 | 保留站内消息，后台可查原因并重试或人工联系。 |
| 人员离职、停用或权限变化 | 停止其不再有权接收的通知，打开旧消息时重新检查访问资格。 |

服务号通知跳转小程序。只完成关注绑定不保证每次消息一定送达，发送成功也不等于用户已读；重要待办仍需站内记录与工作人员跟进。

### 5. 改期与暂停必须有处理出口

当前暂停仍属现行功能，不能沿用旧方案直接写成已下线。建议将改期、加项和暂停合并为订单申请入口，但保留各自业务结果。

- 改期展示原日期、新日期、涉及人员和报价差额。
- 加项明确新增服务、付款安排和相关人员确认。
- 暂停明确原因、期限、负责人，以及是否继续占档、能否付款或结算。
- 暂停结束后必须有恢复、改期、取消退款或进一步人工协调的明确出口。
- 若运营确认不存在暂停业务，再停止新申请并逐单处理存量，不能只删除入口。

## 五、第二批效率优化

| 优化方向 | 具体目标 | 完成标准 |
| --- | --- | --- |
| 客户档案贯通 | 咨询、婚期、顾问、订单和售后关联，避免重复填写。 | 顾问能从客户档案查到最近沟通、当前订单和下一步安排。 |
| 顾问待办 | 新咨询、未分配、今日跟进和流失预警集中处理。 | 每个待跟进客户都有负责人与计划时间。 |
| 问卷续填 | 提供客户答案草稿、继续填写和提交后补充说明。 | 退出或中断后能恢复填写，历史答复不被静默覆盖。 |
| 婚前准备 | 订单展示问卷、人员、时间地点及关键安排的确认情况。 | 服务前能快速识别尚未确认的事项。 |
| 售后统一入口 | 客户描述问题，后台按工单、投诉、退款和回访分工。 | 客户不用先理解内部分类；处理结果、时限和负责人可查。 |
| 人员档案合并 | 资料、作品、资质、套餐与服务范围集中维护。 | 不必到多个位置重复修改同一人员信息。 |
| 经营数据统一 | 成交额、实际收款、退款、待收尾款、平台抽成和人员应付分别统计。 | 同一指标在不同入口口径一致，并能查看构成明细。 |
| 展示月报与业务账目分开 | 人工调整标明原因、版本及用途。 | 展示月报不改变真实订单、付款或结算。 |
| 基础模板简化 | 首页、海报和月报保留必要品牌配置。 | 运营能完成日常修改，不依赖逐次重新设计。 |

## 六、已退役功能：不再作为待开发项

以下范围已在当前工作区的说明与清理记录中退役。本轮方案不再把它们列为“未来考虑删除”。发布环境与历史资料是否完成清理，仍须分别核对。

| 已退役范围 | 重构后的替代或保留内容 |
| --- | --- |
| 钱包、充值、余额支付 | 微信小程序付款、受控线下收款；如有历史余额债务，单独核对并保留处理安排。 |
| 支付宝及旧组合支付 | 现行支持的付款方式；历史付款与退款责任不因入口退役消失。 |
| 旧站外通知渠道及其配置 | 服务号关注绑定、业务推送与站内消息。 |
| 电脑端账号、注册登录、个人中心及收藏 | 电脑展示与小程序引导。 |
| 独立移动网页业务配置及旧发布入口 | 小程序承载业务，服务号承载通知。 |
| 客户侧旧确认函与直接推送 | 人员档期海报、历史材料及订单中的服务约定。 |
| 购物车、方案分享、优惠券与独立套餐预约 | 从人员选择到套餐报价的预约流程。 |
| 分场次预约、场次报价与自助换人 | 当前全天预约；人员无法履约时保留人工协调与售后处理。 |
| 晒单奖励及旧成本报表 | 真实评价、收付款、应收应付和人员结算。 |

旧代码、菜单或素材的残留不等于业务仍开放；不应因为发现残留就重新加入新系统范围。

## 七、建议合并、收缩与按需启用

### 合并入口，保留能力

- 人员资料、套餐、作品、证书统一归入人员档案。
- 客户收藏统一入口，按人员和案例等内容分类。
- 消息、绑定状态及通知设置归入通知中心。
- 改期、加项和暂停归入订单申请。
- 工单、投诉和回访合并客户入口，后台保留不同处理责任。
- 流失预警归入顾问跟进待办。
- 案例、动态、文章与素材归入内容中心，保持内容用途区别。

### 收缩投入，不直接删除现有业务

| 功能 | 默认建议 | 继续投入的依据 |
| --- | --- | --- |
| 活动报名和收费票种 | 独立启用，不占用预约主导航。 | 有持续活动计划、收入与负责人；存量活动继续履约退款。 |
| 复杂社区互动 | 保留必要评论及互动，弱化排行和独立社区运营。 | 互动能够帮助客户咨询或预约。 |
| 开屏广告及首页弹窗 | 默认减少，仅在明确活动时使用。 | 有明确推广目标，且不妨碍正常预约。 |
| 自由装修和多套海报设计 | 固定模板优先，高级编辑按需开放。 | 有高频制作需求和负责人员。 |
| 图片、视频辅助工具 | 保留在辅助工具区。 | 有稳定使用需求，不影响主业务维护。 |
| 深层组织及复杂分成 | 仅展示实际使用的规则。 | 真实团队组织或合同要求，既有约定继续履行。 |
| 吉日拥堵标签与人工榜单 | 基础提示优先。 | 有可靠更新依据，不替代真实档期与经营数据。 |

没有使用量、成交贡献和运营成本数据时，不把“非核心”直接认定为“无价值”。如需停用现行功能，先安排未完成业务、未结款项和历史查询。

| 使用方 | 主要入口 |

| 客户 | 预约服务、案例、我的；订单内承接付款、问卷、变更、售后和评价。 |
| 服务人员 | 今日待办、档期、订单、结算、个人展示；队长增加团队审核。 |
| 顾问 | 我的客户、今日跟进、待处理预警、相关订单。 |
| 运营后台 | 工作台、客户顾问、人员团队、服务报价、档期候补、订单履约、售后评价、收退款与结算、内容活动、通知绑定、基础设置。 |
| 电脑网站 | 品牌、案例、资讯、联系方式及小程序入口。 |

活动入口按业务启用。通知与服务号绑定在“我的”和工作人员工作区保持可发现，不能藏在难以找到的维护设置中。

## 九、实施顺序与验收

### 阶段一：核实现行边界

确认当前工作区、实际部署和历史业务三者的差异；核对退役功能是否仍有未结事项。以本方案中的现行保留范围作为起点，不重复建设已完成的服务号迁移与渠道收缩。

### 阶段二：完善核心业务

优先完成订单统一入口、报价档期一致、付款与履约双进度、手工档期边界、退款结算异常、服务号接收及人工待办。

验收场景：全款预约、定金尾款、线下凭证驳回重交、付款后档期冲突、取消后迟到付款、改期、暂停恢复、部分退款、已结算退款人工处理、人员转账及平台抽成补交。

### 阶段三：提高使用效率

完成问卷暂存、客户档案关联、跟进待办、售后入口合并、人员资料集中维护、内容归并与经营口径统一。

验收场景：客户重复咨询不用重新说明全部需求；问卷退出后可续填；任一未处理事项能找到负责人；任一汇总金额能查到构成明细。

### 阶段四：按需优化外围功能

按实际业务继续优化活动、海报、月报、页面装修和图片工具。未启用的能力不进入主导航；停止业务前先完成已报名活动、承诺服务和未结款项。

### 实际开放前必须确认

- 客户与工作人员均可完成服务号关注绑定，取消关注与解绑行为区分正确。
- 通知跳转小程序后只能查看授权业务；发送失败有可见的站内记录和处理方式。
- 真实微信付款、退款、商家转账及补交结果与业务明细一致。
- 服务已完成但尾款未收的订单不会误取消或丢失应收。
- 手工档期影响可约情况，但不自动形成平台收入与结算。
- 暂停、改期、退款和异常付款均有最终处理出口。
- 海报与月报在真机可保存，导出失败不影响订单履约。
