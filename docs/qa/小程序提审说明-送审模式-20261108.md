# 小程序提审说明 · 送审模式与 UGC

> 决策记录（2026-11-08）：**保留** `feature_switch.mini_program_review_mode`，不整套下线。
> 本文件两大用途：① 提审时可直接粘贴的版本说明；② 开关的运营操作卡与红线。

## 一、提审说明（可直接粘贴到「版本描述 / 审核备注」）

> **一、本版本的用户内容（UGC）功能与内容安全措施**
>
> 本小程序包含用户评价（含追评）与动态评论两类用户生成内容，均设有内容审核机制：
>
> 1. 所有用户发布的评价、追评、评论默认进入后台人工审核队列，审核通过后才对外展示，未通过不对其他用户可见。
> 2. 文本内容在发布时同步调用微信内容安全接口（`wxa/msg_sec_check`），命中风险的内容一律进入待审，不做直接发布。
> 3. 评价与追评支持上传图片，图片在发布时调用微信内容安全异步接口（`wxa/media_check_async`）检测；检测结果返回前、以及检测超时未返回时，内容均保持待审状态，不会提前对外展示。
> 4. 用户昵称、个人资料修改同样接入上述文本检测。
>
> **二、关于后台「小程序送审模式」开关**
>
> 系统后台「设置 → 功能开关」中存在一个全局运营开关 `mini_program_review_mode`（小程序送审模式），**当前值为关闭**。
>
> 该开关的影响范围仅限三处写操作：发表评论、发表评价、追评。开启后由服务端接口统一拒绝上述三类提交，并隐藏小程序内的评论输入入口；**不影响**内容浏览、服务人员展示、档期查询、下单、支付、退款、售后、消息通知等任何其他功能，也不影响已有内容的正常展示。
>
> 补充说明：用户端「发布动态」功能自上线起即为全局关闭状态，与本开关无关。
>
> 该开关为全局开关，开启后对所有用户同时生效，不存在针对审核账号或特定设备的差异化处理。
>
> **三、本次提审状态**
>
> 本次提交版本在审核期间，上述开关保持**关闭**，审核版本与线上版本功能完全一致。审核通过后，线上版本不会通过该开关改变任何已审核功能的可用性。

> ⚠️ 若产品最终决定「审核期开启、过审后关闭」，上面第三节必须改写为如实披露（写明审核期会关闭 UGC 写入口、过审后恢复），并知悉这属于**审核版本与线上版本功能不一致**，有被驳回或事后处罚的风险。技术侧不替产品做这个决定。

## 二、开关的真实影响范围（代码级核对，2026-11-08）

| 入口 | 后端拦截 | 前端隐藏 | 说明 |
|---|---|---|---|
| 发表评价 `POST /api/review/publish` | ✅ `ReviewController:80` | ❌ | 开启后返回「小程序送审模式已开启，暂不支持发表评价」 |
| 追评 `POST /api/review/append` | ✅ `ReviewController:99` | ❌ | 同上，文案为「暂不支持追评」 |
| 发表评论 `POST /api/dynamic/addComment` | ✅ `DynamicController:125` | ✅ `feed-detail.vue` 评论区输入框 | 文案为「暂不支持评论」 |
| 发布动态 `POST /api/dynamic/publish` | ⛔ 永久关闭 | — | `DynamicController:57` 直接返回「动态发布功能已关闭」，**与本开关无关** |
| 浏览 / 订单 / 支付 / 档期 / 售后 | — | — | 完全不受影响 |

结论：开关的**实际**作用面是「三条 UGC 写接口 + 一个评论输入框」。后台开关页的提示文案写的是「隐藏并拦截发布动态、发表评论、发表评价和追评」，其中「发布动态」一项是历史遗留描述——动态发布本来就全局关了，不是这个开关在管。

## 三、运营操作卡

**谁能操作**：拥有「设置 → 功能开关」权限的后台账号（建议只保留 1–2 个运营负责人）。

**怎么开/关**：后台 → 设置 → 功能开关 → 「小程序送审模式」→ 保存。配置走 `ConfigService`，保存时自动清缓存，**秒级生效**，不需要发版、不需要重启。

**变更留痕**（本次新增）：
- 运行时日志：`小程序送审模式开关变更：admin_id=…，before=…，after=…，ip=…`
- 数据库：`la_config` 中 `type='feature_switch' AND name='mini_program_review_mode'` 的 `update_time`

**开启后的自检**（任选其一即可确认生效）：
```bash
# 后端拦截是否生效（未登录会先撞登录校验，登录态下应返回上面的文案）
curl -s -X POST 'https://<域名>/api/review/publish' -H 'token: <用户token>'
```
或在小程序里打开动态详情，评论区输入框应消失。

**回滚**：改回 `0` 保存即可，无需其他操作。

## 四、红线

1. **不要**为了过审临时开启、过审后再关闭。开关是运营工具，不是过审工具。
2. **不要**给审核账号开白名单绕过该开关（代码里也没有这种分支，不要加）。
3. 开关开启期间，用户提交会收到明确的拒绝文案，不要改成静默失败——静默失败会让用户以为发布成功。

## 六、已知 UX 缺口（仅在决定启用开关时才需要处理）

评价、追评的**前端入口没有隐藏**，只有后端拒绝。开关一旦开启，审核员/用户点「写评价」会看到一条错误提示而不是入口消失，观感上像功能坏了。

若确实要在审核期启用，建议先补这两处入口的隐藏（`staff-detail` 评价按钮、订单完成页评价入口），再开启开关；否则优先保持关闭。
