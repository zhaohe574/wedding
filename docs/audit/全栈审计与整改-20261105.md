## 二、问题清单（按严重程度排序）

> 状态说明：**已修复** = 本次已改代码/数据并验证；**待处理** = 已定位、给出方案但未改动（避免超出本次范围或需要产品决策）。

### P0-1 接口异常返回 HTML 错误页，泄露堆栈与绝对路径 【已修复】

- **位置**：`server/app/ExceptionHandle.php`（原实现 `render()` 直接 `return parent::render($request, $e)`）；`server/config/app.php` 的 `show_error_msg`
- **风险点**：框架按 `Accept`/`Content-Type` 判断是否输出 JSON，而前端 GET 请求不带 `Accept: application/json`，于是走 HTML 模板分支。`APP_DEBUG=true` 时模板会渲染异常消息、文件绝对路径、代码片段、调用栈。
- **实测证据**：
  ```
  GET /api/pay/notifyMnp
  → HTTP 500 | text/html | 81805 字节
  → 页面内含 D:\...\server\vendor\w7corp\easywechat\src\Pay\Server.php line 117
  ```
- **影响范围**：
  1. `/api` 与 `/adminapi` 所有未捕获异常（不只是支付回调）都会返回 HTML，前端 axios 拿到字符串，`code` 为 `undefined`，页面表现为「无提示失败」；
  2. 微信支付回调无法按 JSON/XML 契约应答，微信侧会持续重试；
  3. 未鉴权接口（如支付回调、登录、短信）可被用来探测服务器目录结构与依赖版本。
- **修复**：`/api`、`/adminapi` 统一渲染 `{code, show, msg, data, request_id}`；异常写入日志（含 `request_id`、异常类、文件、行号、trace），响应体不含任何路径与堆栈；仅 `RuntimeException`/`InvalidArgumentException`/`LogicException` 回显原文，`PDOException`、`DbException`、`Error`、`TypeError` 一律替换为「服务暂时不可用」。
- **验证**：同一 URL 现在返回 `500 | application/json | 128 字节`；`/api/staff/detail` 等业务失败响应保持原有 `{code:0,show:1,msg:"参数错误"}` 不变；非接口应用（`/nosuchapp/foo`）仍返回 HTML 404，页面型应用行为未变。

### P0-2 SQL 调试日志把会话 token、手机号明文落盘 【已修复】

- **位置**：`server/config/database.php` → `'trigger_sql' => env('app_debug', true)`
- **风险点**：SQL 监听开关直接跟随 `APP_DEBUG`。开发机 `.env` 里 `APP_DEBUG = true`，于是**每一个请求的全部 SQL** 都会写入 `runtime/*/log/*.log`，包括 `WHERE token = '...'` 和用户手机号、地址。
- **实测证据**：
  ```
  runtime/api/log/20261105.log:
  [sql] SELECT * FROM `la_user_session` WHERE `token` = 'a70d0d7cccd6c37fd3d5a73629f6806b' ...
  runtime/adminapi/log/20261105.log:
  [sql] ... WHERE `token` = '48defe43f02408b773f37f3c4802f57d' ...
  ```
  现存日志中共 21 行包含 token 条件。
- **影响范围**：任何能读到 `runtime/` 的人（运维备份、日志采集、目录遍历、误提交）都可直接冒用未过期会话，绕过全部权限校验；同时日志体积被放大数十倍（单日 300KB+），影响磁盘与检索。
- **修复**：`trigger_sql` 改为独立开关 `env('database.debug', false)`，默认关闭，不再受 `APP_DEBUG` 影响；`.example.env` 与本地 `.env` 均标注风险并置为 `false`。
- **验证**：同一请求前后对比日志行数增量 `0`；接口功能无变化。
- **遗留动作**：历史日志需一次性清理（见「五、遗留项」）。

### P1-2 订单列表 N+1 查询：每行 5~7 次额外 SQL 【已修复】

- **位置**：`server/app/adminapi/lists/order/OrderLists.php::lists()`
- **风险点**：`foreach` 内逐行调用 `OrderReceiptService::pending()`、`OrderRefundService::getRefundableAmount()`、`OrderRefundService::hasPendingRefund()`，其中 `getRefundableAmount` 自身还要按支付笔数再查。
- **实测证据**（4 行数据，会话级 `Questions` 计数器）：

  | 指标 | 整改前 | 整改后 |
  | --- | --- | --- |
  | SQL 次数 | 35 | 21 |
  | 与行数关系 | `15 + 5×N` | 常数 |

  逐行查询明细：`order_receipt_request` 计数、`refund` 补偿流水、`payment` 列表、`refund_item` 汇总（每笔支付一次）、`refund` 进行中判定。
- **影响范围**：`page_size` 默认 25 时约 140 次 SQL；`page_type=0`（不分页）或导出场景按 25000 上限计算可达**十万级 SQL**，是后台最典型的慢查询来源，会拖垮数据库连接池。
- **修复**：新增批量方法 `OrderRefundService::getRefundableAmountMap()` / `getPendingRefundOrderIdMap()`、`OrderReceiptService::pendingMap()` / `latestPendingMap()`，按当前页 `order_id` 一次性取回后在内存计算；单笔方法保留，其他调用方不受影响。
- **兼容性**：输出与改造前**逐字节一致**（快照比对通过），并额外做了全量等价性校验：8 笔订单 × 4 个维度（可退金额、进行中退款、待审核收款、最新申请单）0 处差异。
- **同类问题（已顺带修复）**：`app/adminapi/lists/aftersale/TicketLists.php` 每行调用 3 次 `AfterSaleTicket::find()` 仅为读取访问器，改为 1 次。

### P1-3 CORS 同时声明 `*` 与 `Allow-Credentials`，且任意站点可调后台接口 【已修复】

- **位置**：`server/app/common/http/middleware/LikeAdminAllowMiddleware.php`
- **风险点**：`Access-Control-Allow-Origin: *` + `Access-Control-Allow-Credentials: true` 是规范禁止的组合，浏览器会直接拒绝带凭据的跨域请求；同时 `*` 意味着任意站点都能读取后台接口响应（当前认证走 `token` 请求头，风险被削弱，但缺少来源约束）。
- **影响范围**：全部接口；既是功能缺陷（预检失败）也是收敛不足的暴露面。
- **修复**：新增 `[CORS] ALLOWED_ORIGINS` 配置。配置白名单时按 Origin 精确回显并允许凭据、追加 `Vary: Origin`；未配置时保持 `*` 但**不再声明 `Allow-Credentials`**。改用响应对象下发头（原实现直接 `header()` 绕过响应对象），`OPTIONS` 返回 204 并携带完整预检头。
- **验证**：白名单命中/未命中、无 Origin 三种情况均符合预期；本地开发（`admin/.env.development` 直连远端域名）仍可用。

### P1-4 敏感词接口缺少参数校验，导入为 2N 次 SQL 【已修复】

- **位置**：`server/app/adminapi/controller/review/SensitiveWordController.php`、`server/app/common/model/review/SensitiveWord.php::batchImport()`
- **风险点**：
  1. `word` 无长度上限（表字段 `varchar(100)`），超长写入在严格模式下 500、非严格模式下静默截断；
  2. `type`/`level`/`status` 未校验枚举，可写入任意整数，后续按枚举取描述时得到空字符串；
  3. `batchDelete` 的 `ids` 未做类型与数量约束；
  4. `import` 无行数上限、无事务、逐条 `find + create`，导入 1 万条要执行 2 万次 SQL，中途失败留下半截数据。
- **影响范围**：内容安全能力（评论/资料文本检测）依赖该词库，脏数据会直接削弱审核效果。
- **修复**：新增长度（100 字符）、枚举、批量上限（删除 500、导入 2000 行）、控制字符清洗；`import` 去重后分批 `insertAll`，并发唯一键冲突时退回逐条写入并跳过已存在项；补齐 `create_time`/`update_time`（原实现写 0）。
- **验证**：导入 120 条实测 **3 次 SQL**（原实现按每条 2 次推算为 240 次）；重复导入返回 0；库中条数、时间戳正确；探针数据已清理（残留 0）。

### P2-1 前端请求层对「非契约响应」无兜底 【已修复】

- **位置**：`admin/src/utils/request/index.ts`
- **风险点**：拦截器直接解构 `response.data.code`。当响应是 HTML 错误页、网关 502 文本、或字段缺失时，`code` 为 `undefined`，落入 `default` 分支把原始内容当业务数据返回，调用方拿到字符串却按对象使用，报错点与真实原因相距很远。
- **修复**：响应不是对象或缺少 `code` 时，弹出统一提示并抛出带 `request_id` 的 `Error`；`catch` 分支优先展示后端返回的 `msg`（带 `request_id`），不再只显示 `Request failed with status code 500`。

### P2-9 列表单页上限过高，且 `initPage()` 缺少二次收敛 【已加固】

- **位置**：`server/config/project.php` → `lists.page_size_max = 25000`；`server/app/common/lists/BaseDataLists.php::initPage()`
- **风险点**：`ListsValidate` 已经校验 `page_size <= 25000`、`page_no > 0`、`page_type in (0,1)`，所以**不存在「完全无上限」**。真实风险有两点：
  1. 上限本身偏高——单个请求即可拉取 2.5 万行，与 P1-2 的 N+1 叠加后放大成十万级 SQL；
  2. `initPage()` 自身不做任何收敛，完全依赖校验器，属于单点依赖：若某个列表类绕过 `ListsValidate`，或后续有人放宽规则，就会直接失守。
- **影响范围**：128 个 `adminapi` 控制器共用的列表基类；`page_type=0`（不分页）与导出路径都会走到最大条数。
- **加固**：在 `initPage()` 增加 `clampPageSize()` 作为二次防线（`[1, page_size_max]`），`page_no` 下界置 1。**对通过校验的请求行为完全不变**，只是让越界值不再产生负 `OFFSET` 或超大 `LIMIT`。
- **验证**：`page_size=30000` 仍由校验器拒绝（提示「已超出系统限制数量…25000」）；`page_size=20000` 行为不变；`page_no=-1` 仍被拒绝；订单列表快照与整改前一致。
- **建议（需产品确认）**：把交互式列表上限降到 200~500，导出走独立通道；这属于行为变更，本次未动。

### P3-1 `hasPermission()` 与 `v-perms` 语义相反，且未被使用 【待处理】

- **位置**：`admin/src/utils/perm.ts`
- **风险点**：`hasPermission(['a','b'])` 要求**同时具备**（`forEach` 累积），而 `v-perms` 是**任一具备**（`some`）。当前全项目无调用，但作为导出工具函数极易被误用。
- **建议**：删除，或改为与 `v-perms` 一致的 `some` 语义并加注释。

### P3-2 金额比较仍有浮点残留 【待处理】

- **位置**：`FinancialFlow.php:183`、`StaffCompanyFeeUsage.php:53`、`OrderRefundService.php:843` 等处使用 `round((float)$x, 2) !== $y`。
- **风险点**：两侧都 `round` 到 2 位后比较，绝大多数场景成立，但不是严格等价（`0.1+0.2` 类问题在 2 位内通常被抹平）。
- **建议**：涉及「是否相等」的判定统一改为 `MoneyService::yuanToFen()` 后整数比较；`>` / `<` 的大小比较可保留。

### P3-3 后台入口路径硬编码 【待处理】

- **位置**：`admin/vite.config.ts` `base: '/gelinshe0318/'`；`server/route/app.php` 中同名路由；`public/gelinshe0318/`
- **风险点**：安全靠路径混淆，一旦泄露（截图、日志、Referer）即失效；换环境需同时改三处。
- **建议**：保留混淆路径但改为构建期注入的环境变量，并在网关层叠加 IP 白名单/二次认证。

### P3-4 后台路由未使用显式白名单 【待处理】

- **位置**：`server/config/route.php` `url_route_must => false`，`adminapi` 无路由定义。
- **风险点**：控制器/方法即路由，新增文件即自动暴露；虽然 `AuthMiddleware` 会兜底拒绝未登记接口，但暴露面大于必要范围。
- **建议**：为 `adminapi` 生成显式路由表（可由 `scripts/contracts/export-endpoints.mjs` 的输出派生），逐步切换 `url_route_must`。
